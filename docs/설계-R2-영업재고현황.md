## 1. API 계약 7개 (복붙 수준)

### 공통 규약 (R1과 동일)
- 모든 API는 **GET**, 응답 JSON. 금액은 정수(원), 수량은 kg 소수 1자리(`round1`).
- 기간 `from`/`to`는 `YYYY-MM-DD`. 미지정/형식오류 시 `from`=이번달 1일(`monthStartISO()`), `to`=오늘(`todayISO()`) — finreports.mjs와 동일 규칙(로컬 복제).
- **응답 봉투는 전부 집계/목록형** `{ rows: [...], summary: {...} }` (R1 원장형은 R2에 없음). ReportScreen은 `rows`를 그대로 그리드에 세팅, `summaryLine(env)`로 요약 힌트 렌더.
- 에러: `err(c, 400, '메시지')` → `{ error }`.

---

### 1.1 미주문현황 ⭐ — `GET /api/order-missing`
기간 내 **주문이 없는 매출 거래처**를 나열(기존 앱 '주문 누락 체크'). 각 거래처의 마지막 주문일·마지막 판매일·미주문 경과일수를 표시해 후속 영업 우선순위 판단.

**요청**: `?from=2026-07-01&to=2026-07-31&basis=order`
- `basis` 선택: `order`(기본, 주문서 기준 — 기간 내 `doc_type='order'` 없으면 미주문) / `order_sale`(주문·판매 기준 — 기간 내 `order`·`sale` 둘 다 없으면 미거래). 로스터리 실무상 주문서 단계를 건너뛰고 바로 판매하는 거래처를 잡기 위한 토글.

**응답**:
```json
{
  "rows": [
    { "partner_id": 2, "code": "2208165848", "name": "(주)이카운트", "pay_cycle": "당일",
      "last_order": "2026-06-15", "last_sale": null, "days_since": 26 }
  ],
  "summary": { "count": 20, "basis": "주문서" }
}
```
- 대상 거래처: `partner.active=1 AND partner.partner_type LIKE '%매출%'`(매출·매출+매입). 
- `last_order`/`last_sale`: 전 기간(제한 없음)의 `MAX(io_date)`. 없으면 `null`.
- `days_since`: `todayISO`와 기준일(basis=order→last_order, basis=order_sale→max(last_order,last_sale))의 일수 차. 기준일이 `null`(한 번도 없음)이면 `null`(그리드 정렬 시 최우선 노출 대상).
- `summary.basis`: 표시용 라벨(`주문서`/`주문·판매`).

### 1.2 / 1.3 / 1.4 견적서·주문서·발주서 현황 — `GET /api/quote-status` · `/api/order-status` · `/api/po-status`
이카운트 현황은 **품목 라인 단위 집계**(목록 화면 `DocChainList`와 별개 — 목록은 전표 1행, 현황은 라인 1행). 셋은 `docStatusReport(type, c)` 한 함수로 구현하고 3개 라우트만 얇게 부착(finreports의 수금/지급 패턴과 동일).

**요청**: `?from&to&partner_id&item_id&status`
- `partner_id` 선택(거래처 코드도움), `item_id` 선택(품목 코드도움 — 해당 품목 라인만), `status` 선택: `전체`(기본)/`대기`/`완료`.

**응답**(주문서현황 예):
```json
{
  "rows": [
    { "io_date": "2026-07-08", "doc_no": "20260708-1", "partner_name": "(주)이한에프엔비",
      "item_code": "00001", "item_name": "[과테말라] 산타펠리사 …", "qty": 10, "price": 22000,
      "supply_amt": 220000, "vat_amt": 22000, "amount": 242000, "status": "대기", "time_date": "2026-07-12", "memo": "" }
  ],
  "summary": { "count": 2, "qty": 15, "supply": 370000, "vat": 37000, "total": 407000 }
}
```
- 그레인: `doc_line` 1행 = rows 1행. `WHERE d.doc_type=? AND d.io_date∈[from,to]` (+ 선택 필터).
- `amount` = `supply_amt + vat_amt`(라인 합계). `partner_name`: 견적/주문=매출처, 발주=매입처(같은 컬럼).
- `time_date`: 주문서/발주서=납기일자, 견적서=`null`(컬럼은 공통, 견적은 빈 값).
- `summary`: 라인 건수·수량합·공급/부가세/합계합.

### 1.5 판매구매 집계표 — `GET /api/sales-purchase-summary`
그룹 기준 선택(일별/월별/거래처별/품목별) × 판매/구매 피벗. 수량/공급가액/부가세/합계.

**요청**: `?from&to&tx=sale&group=day`
- `tx` 선택: `sale`(기본)/`purchase`.
- `group` 선택: `day`(기본)/`month`/`partner`/`item`.

**응답**(tx=sale, group=day):
```json
{
  "rows": [
    { "code": "2026-07-10", "label": "2026-07-10", "qty": 20, "supply": 440000, "vat": 44000, "total": 484000 },
    { "code": "2026-07-15", "label": "2026-07-15", "qty": 10, "supply": 300000, "vat": 30000, "total": 330000 }
  ],
  "summary": { "count": 2, "qty": 30, "supply": 740000, "vat": 74000, "total": 814000 }
}
```
- 그룹 키/라벨 매핑: `day`→`code=label=io_date`, `month`→`YYYY-MM`, `partner`→`code=거래처코드/label=거래처명`, `item`→`code=품목코드/label=품목명`.
- **컬럼은 8조합 전부 동일**(`code/label/qty/supply/vat/total`) → 단일 ReportDef로 커버(§3.4).
- `total` = `supply + vat`. `summary.total` = 전체 doc 헤더 합계와 일치(§2.7 검증).

### 1.6 기타이동현황 — `GET /api/other-moves`
창고이동/자가사용/불량처리/재고조정 통합 이력. **grain = stock_ledger 1행**(수불부와 동일한 진실 소스), 유형 필터.

**요청**: `?from&to&type=전체`
- `type` 선택: `전체`(기본)/`창고이동`(move)/`자가사용`(self_use)/`불량처리`(defect)/`재고조정`(adjust).

**응답**:
```json
{
  "rows": [
    { "io_date": "2026-07-20", "doc_no": "20260720-1", "type": "창고이동", "item_code": "00001", "item_name": "…",
      "warehouse_name": "본사창고", "io_type": "기타출고", "qty": -15, "memo": "" },
    { "io_date": "2026-07-20", "doc_no": "20260720-1", "type": "창고이동", "item_code": "00001", "item_name": "…",
      "warehouse_name": "로스팅공장", "io_type": "기타입고", "qty": 15, "memo": "" }
  ],
  "summary": { "count": 4, "net_qty": -7 }
}
```
- `qty`: **stock_ledger.qty 부호 그대로**(기타입고 +, 기타출고 −) — 유형별 부호 규칙은 §2.5.
- `warehouse_name`: 해당 원장 행의 창고(창고이동은 출고창고·입고창고 2행으로 자연 분해).
- `memo`: `COALESCE(NULLIF(dl.remarks,''), d.memo)` — 재고조정은 라인 remarks(`장부 … → 실사 … (조정 …)`), 그 외는 전표 적요.
- `summary.net_qty`: rows qty 합(창고이동은 상쇄되어 0 기여 — 순 재고증감 확인용).

### 1.7 재고변동표 — `GET /api/stock-flow`
기간 내 **품목 전체**의 이월/입고/출고/잔량. 재고수불부(`/api/stock/ledger`)의 **전 품목 버전**이며 집계 방식이 수불부와 동일(품목 drill-down 시 숫자 일치).

**요청**: `?from&to&item_type=전체&show=active`
- `item_type` 선택: `전체`(기본)/`원재료`/`부자재`/`제품`/`상품`(`item.item_type` 필터).
- `show` 선택: `active`(기본, 이월·입고·출고가 모두 0인 품목 제외)/`all`(전 품목).

**응답**:
```json
{
  "rows": [
    { "item_id": 3, "code": "00001", "name": "[과테말라] 산타펠리사 …", "spec": "", "unit": "kg",
      "opening": 70, "in_qty": 65, "out_qty": 42, "closing": 93 }
  ],
  "summary": { "count": 2 }
}
```
- `opening` = `Σ qty WHERE io_date < from`(경계 `<`, §2.4). `in_qty` = `Σ qty(qty>0)`, `out_qty` = `Σ −qty(qty<0)`, 둘 다 `io_date∈[from,to]`. `closing` = `opening + in_qty − out_qty`.
- 전 창고 합산(R2는 창고 필터 미제공 — 창고별 상세는 수불부에서). 수량은 품목마다 단위가 달라 **합계행 없음**(그리드 bottomCalc 미사용).

## 2. 서버 계산 규칙

`salesreports.mjs`는 `db`(db.mjs), `err`/`isValidDate`/`todayISO`/`round1`(ledger.mjs)를 import. `monthStartISO()`는 finreports/accounting과 동일한 로컬 복제.

### 2.1 미주문 판정 기준 (⭐ 핵심)
- **대상**: `partner.active=1 AND partner.partner_type LIKE '%매출%'`. (현재 실데이터 21개 거래처 전부 `매출`.)
- **미주문 판정**(`basis=order`, 기본): 아래 EXISTS가 거짓인 거래처만 rows에 포함.
  ```sql
  NOT EXISTS (SELECT 1 FROM doc o
              WHERE o.doc_type='order' AND o.partner_id=p.id AND o.io_date>=:from AND o.io_date<=:to)
  ```
- **주문·판매 기준**(`basis=order_sale`): `o.doc_type IN ('order','sale')`로 확장(신규 판매도 '주문'으로 간주 — 주문서 단계를 생략하는 거래처 대응).
- `last_order`=`MAX(io_date) WHERE doc_type='order' AND partner_id=p.id`(전 기간), `last_sale`=동일하게 `sale`. `days_since`는 서버 JS에서 `Math.floor((Date.parse(today)-Date.parse(기준일))/86400000)`, 기준일 없으면 `null`.
- **설계 결정**: 플랜 문구("주문(order)이 없는")를 기본값으로 충실히 따르되, 실무 유연성을 위해 `basis` 토글을 추가(범위 확장 아님 — 판정 소스만 선택). 마지막 주문일/판매일을 **둘 다** 노출하라는 플랜 요구를 그대로 반영.

### 2.2 견적/주문/발주 현황 (라인 단위)
- `docStatusReport(type, c)` 공용 함수, `type ∈ {'quote','order','purchase_order'}`. `doc_line dl JOIN doc d`(+`item i`, `LEFT JOIN partner p`)에서 `WHERE d.doc_type=? AND d.io_date BETWEEN ? AND ?`.
- 선택 필터: `d.partner_id=?`, **`dl.item_id=?`**(품목 지정 시 그 라인만), `d.status=?`(전체면 미전송). `ORDER BY d.io_date, d.id, dl.line_no`.
- `amount = dl.supply_amt + dl.vat_amt`. summary는 라인 수·수량합(`round1`)·공급/부가세/합계 합.
- 견적서는 `time_date`가 항상 `null`(스키마상 order/purchase_order만 납기 보유).

### 2.3 판매구매 집계표 그룹핑
- 소스: `doc_line dl JOIN doc d`(+`item i`, `LEFT JOIN partner p`), `WHERE d.doc_type=:tx AND d.io_date∈[from,to]`. 4개 group 모두 **doc_line 기준 집계**로 통일 → `group=item`까지 한 쿼리 형태로 커버.
- 그룹 키 표현식:
  | group | GROUP BY / code | label |
  |---|---|---|
  | `day` | `d.io_date` | `d.io_date` |
  | `month` | `substr(d.io_date,1,7)` | 동일 |
  | `partner` | `p.code` | `p.name` |
  | `item` | `i.code` | `i.name` |
- 집계값: `qty=round1(SUM(dl.qty))`, `supply=SUM(dl.supply_amt)`, `vat=SUM(dl.vat_amt)`, `total=supply+vat`. `ORDER BY code`.
- **합계 일치 보장**: `Σ supply` == `SUM(doc.total_supply)`, `Σ vat` == `SUM(doc.total_vat)`, `Σ total` == `SUM(doc.total_amount)` (doc 헤더 캐시는 라인 합의 롤업이므로 구조적으로 일치 — §2.7 검증 PASS). group=partner에서 `partner_id`가 NULL인 라인(판매/구매엔 없음)은 발생하지 않음.

### 2.4 재고변동표 이월 경계 (수불부와 동일)
- **이월 = `Σ stock_ledger.qty WHERE item_id=? AND io_date < from`** — 경계 `<`(from 당일은 이월이 아니라 기간 입출고에 포함). `reports.mjs`의 재고수불부(:52-59)와 **문자 그대로 동일한 경계**.
- 입고 = `Σ qty (qty>0)`, 출고 = `Σ (−qty) (qty<0)`, 기간 필터 `io_date>=from AND io_date<=to`. 잔량 = `opening + in − out`.
- **수불부 일치성**: 재고변동표의 한 품목 잔량 == 그 품목 수불부 `closing` == `Σ qty(io_date<=to)`(전체 누계). 창고이동(move)은 전 창고 합산 시 기타출고(−)·기타입고(+) 두 다리가 **입고·출고 양쪽에 동일 수량 계상**되어 잔량에는 영향 없음 — 이는 수불부(전 창고)의 거동과 **정확히 일치**하며 의도된 동작(§2.7에서 move 15가 in·out 양쪽에 반영됨을 확인).
- `show=active`: `opening=0 && in=0 && out=0`인 품목 행을 JS 필터로 제외(마스터 57품목 중 무활동 품목 억제).

### 2.5 기타이동 통합 시 유형별 수량 부호
grain을 **stock_ledger 행**으로 잡으면 부호가 자동으로 진실을 따른다(`buildMoveLedgerRows`, ledger.mjs:121-135와 일치):

| doc_type | 라벨 | 생성 원장 행 | rows.qty 부호 |
|---|---|---|---|
| `move` | 창고이동 | 출고창고 `기타출고`(−qty) + 입고창고 `기타입고`(+qty) **2행** | −qty, +qty |
| `self_use` | 자가사용 | 창고 `기타출고`(−qty) **1행** | −qty |
| `defect` | 불량처리 | 창고 `기타출고`(−qty) **1행** | −qty |
| `adjust` | 재고조정 | diff(=실사−장부)≠0이면 `기타입고`(+diff) 또는 `기타출고`(−diff) **1행**, diff=0이면 **행 없음** | ±diff |

- 즉 `qty`는 언제나 `stock_ledger.qty` 그대로. 별도 부호 재계산 없음. 재고조정이 실사=장부(diff 0)면 원장 행이 없어 목록에도 미노출(원장이 유일한 진실이라는 규칙 준수).
- SQL: `stock_ledger sl JOIN doc d ON d.id=sl.doc_id JOIN item i LEFT JOIN doc_line dl ON dl.id=sl.doc_line_id WHERE d.doc_type IN (선택) AND sl.io_date∈[from,to] ORDER BY sl.io_date, sl.id`.

## 3. ReportScreen 재사용 + 정의 7개

### 3.1 ReportScreen `'item'` 필터 kind 추가 (유일한 엔진 손질 — 가산적 3줄)
견적/주문/발주 현황의 **품목 코드도움**을 위해 `'item'` kind가 필요. R1 CodeHelp 분기는 이미 "account가 아니면 `r.id` 반환"이라 **선택 로직·렌더는 무수정**으로 품목 id를 그대로 돌려준다(품목 필터값 = `item_id`). 아래 3곳만 가산적으로 확장(기존 5종 동작 불변):

```ts
// (1) 타입 유니온 — 'item' 추가
export type FilterKind = 'date-range' | 'account' | 'partner' | 'item' | 'select' | 'as-of';

// (2) initLabels — account/partner와 함께 item도 라벨 상태 초기화(저장 탭 스냅샷 정확도)
const initLabels = (def: ReportDef): Record<string, string> => {
  const l: Record<string, string> = {};
  for (const f of def.filters) if (f.kind === 'account' || f.kind === 'partner' || f.kind === 'item') l[f.key] = '';
  return l;
};

// (3) CodeHelp 타이틀 폴백(선택) — 라벨을 넘기므로 필수는 아니나 명확성 위해
title={helpFilter.label ?? (helpFilter.kind === 'account' ? '계정과목' : helpFilter.kind === 'item' ? '품목' : '거래처')}
```
- 렌더: account/partner 분기는 함수 말미 **기본 `return`**(lookup input)이라 `'item'`이 자동으로 동일 렌더. **수정 불필요.**
- 선택값: `const val = helpFilter.kind === 'account' ? String(r.code) : String(r.id);` — item은 `r.id` 사용(기존 코드 그대로). **수정 불필요.**
- 기본 endpoint 폴백(`'/api/partners'`)은 item에서 안 쓰이지만(항상 `helpEndpoint:'/api/items'` 지정), 원하면 `helpFilter.kind==='item' ? '/api/items' : …`로 방어 가능(선택).
- `/api/items`는 `masters.mjs`가 `{id, code, name, …}` 반환(코드도움 계약 충족 — 확인 완료).

> 이 확장은 변형 화면이 아니라 엔진의 표준 필터 확장이다. 이후 R3+ 보고서에서도 품목 코드도움을 재사용한다.

## 5. 결정 근거 · 주의

1. **파일 겹침 0 유지**: 신규 현황은 `salesreports.mjs`로 분리(vouchers/moves/reports 무수정), index.mjs 1줄. 마이그레이션 없음(전부 기존 테이블 파생) → R3=007 번호 보존.
2. **개별 화면 0개**: 집계표 컬럼이 group×tx 전 조합에서 고정이라 `select+mapValue`로 완결. 플랜이 남긴 "불가능한 변형만 개별 화면" 조건이 R2에선 발생하지 않음.
3. **엔진 손질은 `'item'` kind 3줄뿐**: CodeHelp가 이미 non-account를 `r.id`로 반환하므로 렌더·선택 로직 무수정. 가산적·하위호환(기존 7종 회귀 없음), 이후 라운드에도 재사용.
4. **재고변동표 = 수불부 전 품목 버전**: 이월 경계 `io_date<from`·raw ledger 집계를 수불부와 **문자 그대로 동일**하게 두어 두 보고서 숫자가 구조적으로 일치. 창고이동의 입고·출고 양다리 계상은 전 창고 합산의 정상 거동(잔량 불변).
5. **기타이동 부호 = 원장 진실**: grain을 stock_ledger로 잡아 `buildMoveLedgerRows`의 부호를 그대로 승계(move ±2행, self_use/defect −, adjust ±diff, diff 0은 미노출). 별도 부호 로직 없음 → 재고와 항상 정합.
