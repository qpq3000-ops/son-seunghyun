# 01. 프로젝트 기획서 — 나만의 로스팅 ERP (이카운트 클론)

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | **로스팅 ERP** (가칭) — 이카운트 ERP 기능을 복제한 개인용 ERP |
| 사용자 | 1인 (커피 로스팅 사업자 본인). 배포/판매 없음 |
| 목표 | 이카운트 ERP의 기능·업무 흐름·화면 패턴을 **카피 수준**으로 재현하되, 로스팅 업무(기존 `index.html` 앱의 강점)를 1급 기능으로 통합 |
| 실행 환경 | 본인 PC 로컬 실행 (localhost 웹앱). 인터넷 없이 완전 동작, 데이터는 내 파일로 소유 |
| 개발 방식 | Claude Code(Opus 4.8)가 전체 코드 생성 — `docs/03-오퍼스-작업-프롬프트.md`의 프롬프트로 진행 |
| 참조 문서 | `docs/00-현재-업무-분석.md`(내 업무), `docs/02-이카운트-기능-분석.md`(이카운트 스펙 140개 메뉴) |

### 원칙
1. **기능은 이카운트를 따른다** — 메뉴명, 업무 흐름(견적→주문→판매, 발주→구매, BOM→작업지시→생산입고), 화면 패턴(검색패널+그리드, 헤더+품목라인 전표, 끌어오기)을 그대로 재현
2. **규모는 1인에 맞춘다** — 다중 사용자·권한·결재 등 조직 기능은 제외하고, 그 자리에 로스팅 특화 기능을 넣는다
3. **데이터가 자산이다** — 단일 SQLite 파일, 자동 백업, 언제든 엑셀로 내보내기
4. **저작권 안전** — 이카운트의 코드/이미지/문구를 복사하지 않고 기능과 개념만 재현 (개인 사용)

## 2. 범위 정의 (이카운트 대비 In / Out)

### ✅ 포함 (In)
| 이카운트 영역 | 클론 범위 |
|---|---|
| 재고Ⅰ 기초등록 | 품목등록(품목구분: 생두/부자재/제품, 안전재고, 단위), 창고등록, 거래처등록, 단가관리(거래처별 특별단가 = 기존 "예외단가"), 프로젝트 |
| 재고Ⅰ 영업관리 | 견적서 → 주문서 → 판매 (끌어오기 전환), 거래명세서 인쇄, 판매현황, 수금입력, 거래처별 미수금(채권) + **입금주기(당일/월별)** |
| 재고Ⅰ 구매관리 | 발주서 → 구매 (끌어오기), 구매현황, 지불입력, 미지급금, **생두 단가비교(업체별 최근가/최저가)** |
| 재고Ⅰ 생산/외주 | BOM(생두→제품, 수율 반영), **작업지시서 = 로스팅시트**(품목별 합산, 배치 자동계산 ÷5kg 올림, 순서 조정), 생산입고(생산전표생성 — 불출+입고 동시 처리), 소요량계산(간이) |
| 재고Ⅰ 기타이동 | 창고이동, 자가사용(샘플/시음), 불량처리, 재고조정(실사→조정 2단계) |
| 재고Ⅰ 출력물 | 재고현황, 창고별재고현황, 재고수불부, 집계표(일/월/거래처/품목별), 이익현황 |
| 재고Ⅱ | 로트No. 관리(로스팅 배치 = 로트, 생두 로트 추적) — 간이 구현 |
| 회계Ⅰ | 판매/구매/수금/지불 저장 시 **자동분개** → 분개장, 계정별원장, 거래처원장, 매입매출장(부가세: 공급가액/세액 분리, 원미만 절사), 월별손익, 간이 일반전표(경비 입력) |
| 회계Ⅱ | 자금현황(통장/현금 잔액 간이), 비용관리(경비 집계) |
| 그룹웨어 | 일정관리(달력 = 로스팅 회차 + 납기 + 실사일), 메모 보드, **거래처 안내 메시지 생성+복사**(기존 앱 이식) |
| Self-Customizing | 환경설정(부가세 방식, 배치 kg 등), 입력화면 항목 표시/숨김(축소판), 인쇄 양식 선택, 엑셀 업로드/다운로드, 백업/복원 |
| 공통 UI | 상단 대메뉴 + 멀티 탭(MDI) + 즐겨찾기, 검색조건 저장 탭, 코드도움 팝업, 저장 후 연속입력, 메인 대시보드(포틀릿) |

### ❌ 제외 (Out) — 1인 사용에 불필요하거나 외부 인프라 필요
- 전자세금계산서 국세청 전송, 계좌/카드 스크래핑 연동 (→ 홈택스/은행에서 처리, ERP에는 기록만)
- 급여·4대보험·원천세·연말정산 정밀 계산 (→ 일반전표 경비 입력으로 대체)
- 전자결재, 쪽지/메신저, 사용자 권한, 다중 로그인, 모바일 앱 전용 기능
- WMS·바코드 스캐너 연동 (2차 검토), POS(판매입력Ⅱ), 수입비용, 외주관리(외주공장 없음)

## 3. 시스템 구성 (기술 스택 — 조사 결과 채택)

```
[브라우저 localhost:8010]
  Vite + React + TypeScript (SPA)
  Tabulator (MIT) — 이카운트식 엑셀형 그리드 (인라인 편집·범위선택·클립보드·XLSX)
  @media print CSS — 거래명세서/견적서 A4 인쇄 (PDF는 브라우저 저장)
        │ REST (fetch)
[로컬 Node 서버]
  Hono + better-sqlite3 (동기 API, 단순)
        │
[데이터]  data/erp.sqlite (단일 파일 = 백업 단위)
          data/backup/erp-YYYYMMDD-HHmm.sqlite (실행 시·저장 N회마다 자동 백업)
```

- 실행: `시작.bat` 더블클릭 → `npm start` → 브라우저 자동 오픈. 완전 오프라인
- 선정 근거(상세는 02 문서 "기술 레퍼런스 분석"): SQLite 단일 파일 = 복사가 곧 백업, better-sqlite3 동기 API로 버그 여지 최소, Tabulator는 엑셀식 편집·클립보드가 전부 MIT 무료 (AG Grid는 범위선택/붙여넣기가 유료), Claude가 가장 잘 다루는 스택
- 기존 Firebase 의존 제거 — 기존 앱의 JSON 백업을 **이관 스크립트**로 가져온다

## 4. 데이터 모델 방향 (ERPNext 축소 이식)

핵심 설계 규칙 — **모든 화면이 이 3개 원장 위에서 동작한다**:

1. **전표(문서) 공통 패턴**: `doc`(헤더: 전표번호, 일자, 유형, 거래처, 창고, 상태) + `doc_line`(품목, 수량, 단가, 공급가액, 부가세). 견적/주문/판매/발주/구매가 같은 구조를 공유하고 `doc_type`으로 구분. 끌어오기 = 원본 doc 참조(`source_doc_id`) + 진행상태 갱신
2. **재고수불원장 `stock_ledger`(append-only)**: 전표 저장 시 (일자, 품목, 창고, 입출구분, 수량, 원천전표) 행 생성. 재고현황·수불부·창고별재고는 전부 이 원장의 집계 뷰. 전표 수정/삭제 시 해당 원장 행 재작성
3. **분개원장 `journal` + `journal_line`**: 차변/대변 합계 일치를 저장 시점에 강제. 판매→(외상매출금/매출/부가세예수금), 구매→(원재료/부가세대급금/외상매입금), 수금·지불→(보통예금 등) 자동분개 템플릿
4. **금액은 원 단위 정수(INTEGER)**, 부가세 = 공급가액×10% 원미만 절사(설정으로 반올림 선택). **수량은 kg 소수 1자리**(0.1 단위)
5. 마스터: `item`(품목구분: 원재료/부자재/제품/상품, 단위, 입출고단가, 안전재고, 세트여부), `partner`(거래처: 입금주기, 담당 연락처, 메시지 템플릿), `warehouse`(창고/공장 구분), `price_special`(거래처×품목 특별단가 + 적용 우선순위), `bom`(제품→생두 소요량, **수율%** — 로스팅 중량 손실 반영), `lot`(로스팅 배치/생두 로트), `account`(계정과목), `project`
6. 부속: `calendar_event`, `memo`, `settings`, `message_template`

## 5. 화면 구조 (나만의 ERP 메뉴맵)

이카운트 메뉴명을 유지하되 1인용으로 재편성한 최종 메뉴 트리:

```
[대시보드]  오늘의 로스팅 · 주문 누락 체크 · 미수금 TOP · 안전재고 미달 · 이번달 매출/매입
[영업]      견적서입력/조회 · 주문서입력/조회 · 판매입력/조회 · 판매현황 · 수금입력 · 미수금현황 · 거래처 메시지
[구매]      발주서입력/조회 · 구매입력/조회 · 구매현황 · 지불입력 · 미지급금현황 · 생두 단가비교
[생산]      BOM등록 · 로스팅시트(작업지시) · 생산입고 · 생산현황/수율분석 · 소요량계산
[재고]      재고현황 · 창고별재고현황 · 재고수불부 · 창고이동 · 자가사용 · 불량처리 · 재고조정 · 로트조회
[회계]      매출매입장(부가세) · 분개장 · 계정별원장 · 거래처원장 · 월별손익 · 일반전표(경비) · 자금현황
[일정]      달력(로스팅/납기/실사) · 메모
[기초등록]  품목 · 거래처 · 창고 · 단가관리 · 프로젝트 · 계정과목
[설정]      환경설정 · 입력화면설정 · 인쇄양식 · 엑셀 업로드/다운로드 · 백업/복원 · 기존앱 데이터 이관
```

핵심 업무 시나리오 (기존 앱 → ERP 승격):
1. **주간 로스팅 사이클**: 달력에서 로스팅일 선택 → 주문서입력(거래처 누락 체크 UI) → 로스팅시트에서 품목별 합산·배치 확인·순서 조정 → 생산입고 저장(생두 차감·제품 입고·로트 생성) → 판매 전환(끌어오기)·거래명세서 출력 → 포장 체크 → 안내 메시지 복사 발송
2. **월말**: 미수금현황(월별 입금처 일괄 수금) → 매입매출장으로 부가세 자료 확인 → 월별손익 확인
3. **생두 구매**: 발주서 → 입고 시 구매 전환 → 단가비교로 업체 선정 참고

## 6. 단계별 로드맵 (오퍼스 작업 단위)

| Phase | 내용 | 완료 기준 (DoD) |
|---|---|---|
| **0. 뼈대** | 프로젝트 셋업(Vite+Hono+SQLite), DB 마이그레이션, 공통 UI(대메뉴/멀티탭/그리드/코드도움/검색패널/토스트), 기초등록 4종(품목/거래처/창고/단가) | `npm start` 한 번에 실행. 품목·거래처 등록/수정/삭제, 그리드 편집 동작 |
| **1. 영업·구매·재고** | 전표 공통 엔진(doc/doc_line/stock_ledger), 주문→판매→수금, 발주→구매→지불, 끌어오기, 기타이동 4종, 재고현황/수불부, 거래명세서 인쇄, **기존 JSON 데이터 이관** | 주문→판매→수금 왕복 후 재고·미수금·수불부 숫자가 손으로 계산한 값과 일치. 기존 앱 데이터가 보임 |
| **2. 생산(로스팅)** | BOM(수율), 로스팅시트(배치계산·순서), 생산입고(불출+입고 동시, 로트), 생산현황/수율분석, 달력 통합 | 로스팅 1회차 전체 사이클이 ERP만으로 처리됨. 생두 재고가 수율 반영되어 차감 |
| **3. 회계** | 자동분개 엔진, 분개장/계정별원장/거래처원장, 매입매출장(공급가액/세액), 월별손익, 일반전표(경비), 자금현황 | 판매·구매가 자동으로 장부에 나타나고 차대변 일치. 월별손익이 매출-매입-경비와 일치 |
| **4. 마감 품질** | 대시보드 포틀릿, 메시지 생성, 단가비교, 집계표/이익현황, 엑셀 IO, 자동백업, 인쇄양식 선택, 안전재고 경고 | 기존 앱을 완전히 대체 — index.html 없이 한 주 업무 가능 |
| **5. (선택) 고도화** | 로트 추적(생두→배치→판매처), 간이 MRP(소요량계산), 판매계획 대비 실적, 검색조건 저장 탭 | 필요 시 |

각 Phase는 `docs/03-오퍼스-작업-프롬프트.md`의 전용 프롬프트로 시작한다. Phase 1이 끝나면 즉시 실사용을 시작하고, 쓰면서 발견한 불편을 다음 Phase 프롬프트에 반영하는 것을 권장.

## 7. 확정 사항 업데이트 (2026-07-10 — 실데이터·API·사내배포 반영)

사용자 PC의 `ecount` 폴더(병행 분석 프로젝트)에서 확보된 사실을 반영한 최신 결정사항. **기존 장(2~6장)과 충돌 시 이 장이 우선한다.**

1. **프로젝트 본질 = 이카운트 "대체"** (연동 아님). 최종 목표는 이카운트 구독 해지. 해지는 병행 운영으로 숫자 검증 후에만.
2. **배포 범위 변경**: 외부 배포는 없지만 **사내에서는 공유**한다 → 서버는 LAN 바인딩(같은 네트워크에서 `http://<PC IP>:8010` 접속 가능, 구현됨). 사용자 계정/간단 권한은 Phase 5에서 추가 검토.
3. **실데이터 확보** (블랙크랙원 로스터스, 회사코드 630469):
   - 품목 57건 — 원두 `00xxx`(제품/상품) ↔ 생두 `a00xxx`(원재료) **쌍 구조** (자동 짝 연결 23쌍, `item.paired_item_id`)
   - 거래처 21곳 (B2B 위주, 이카운트는 사업자번호를 거래처코드로 사용)
   - 판매내역 2,052라인 (2024.1~2026.7, 총매출 3.0억 / bco 블랜딩이 80% / 카페그래비티가 55%) → **Phase 1 전표 엔진 완성 후 이관**. 거래처명 병합 방침 확정: 카페엘리스=카페앨리스, 전미용=전미옥님 빨래방, 어울림센터→어울림센터(둔포), 나머지 3곳 신규
4. **이카운트 Open API 제약 (실측)**: 조회 가능 = 품목·재고현황·창고별재고뿐. 거래처/판매/회계 조회 API 없음(404) → **엑셀 이관 병행 필수**. 쓰기 API는 사용자 승인 없이 호출 금지(이 프로젝트는 조회만 구현). API는 이카운트에 등록된 공인 IP에서만 호출 가능 → 사용자 PC에서 실행 시에만 동작. 인증키는 `data/ecount.config.json`(gitignore)에만 보관, 커밋·채팅 노출 금지.
5. **마이너스 재고의 교훈**: 이카운트 재고에서 원두가 전부 마이너스(-8,565 등) = 생산입고를 입력하지 않는 운영. 판매 8,512 vs 재고 -8,565로 숫자 검증됨 → **Phase 2의 "로스팅 입력"(생두 차감+원두 입고+수율을 한 화면에서)이 이 프로젝트의 최우선 차별 기능**임이 실증됨.
6. **세무·회계 전문 기능은 범위 외 확정**: 부가세신고서·전자세금계산서는 만들지 않고, 매출·매입 집계표를 세무사에게 전달하는 방식. (과도기: 이카운트 회계 자동분개 API로 하이브리드 운영 가능성 메모)
7. **판매입력 UX 우선순위**: 매출의 80%가 반복 주문 → "지난 주문 복사" / 거래처 선택 시 최근 품목·단가 자동 제안을 Phase 1 판매입력에 포함.
8. **병행 프로젝트와의 관계**: 사용자 PC의 `ecount/app`(Express+순수HTML 뼈대)은 분석·검증용으로 유지하고, **본 저장소가 메인 구현**이다. `ecount/docs-api/`(이카운트 API 공식 문서 수집본)와 분석 문서들을 스펙 소스로 사용한다.
