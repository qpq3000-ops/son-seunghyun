# 설계-R11-입력화면 (영업 입력 실물화 + 회계 입력 실물화)

> 진실 자료: `docs/참고-실물실측-20260712.md` **§12**(영업·회계 입력 화면 4차 실측).
> 목표: 견적서·주문서 입력화면과 회계 입력화면(현금거래·매출매입거래)을 실물 필드 구성/툴바/하단바로 실물화.
> 범위는 §12가 전부다. 이 이상 확장 금지.

## 0. 대원칙 (R11 불변 규칙)

- **저장 로직은 전부 기존 API 재사용.** R11은 *입력 화면(UI 계층)* 실물화이지 새 저장엔진이 아니다.
  전표엔진(doc/journal/receipt), 자동분개(차=대 강제), 채번(nextSeqNo)을 **그대로 사용**한다.
- **신규 서버 API = 0건, 신규 마이그레이션 = 0건.** (아래 §2에서 재사용 계약만 정리)
- `client/src/styles.css`는 **append-only** — R11-A/R11-B 블록을 파일 끝에 각각 추가. 기존 줄 수정 금지,
  `r8-*`/`r9-*`/`r10-*`·`voucher-*`·`form-grid` 등 기존 클래스 **재사용 우선**.
- 기존 메뉴 **id 동결**(삭제·개명 금지). 추가·라벨변경·그룹재배치는 허용.
- 금액 INTEGER(원), 수량 REAL(kg). DataGrid(Tabulator) 사용.
- 국세청/은행/전자결재/바코드 등 실연동은 **동작 없는 stub**(disabled + title 안내) 유지.
- 검증 시 서버 기동·포트 8010 금지. DB 쓰기 검증은 **ROLLBACK 트랜잭션**으로만.

## 1. 패키지 분할 (파일 소유 · 겹침 0)

| 패키지 | 파일 | 역할 |
|---|---|---|
| **서버** | (신규 0) — `server/vouchers.mjs`·`gl.mjs`·`receipts.mjs`·`accounting.mjs` **재사용만** | 아래 §2 계약 확인용. 코드 변경 없음 |
| **클라A** (견적·주문) | `client/src/screens/DocChainScreen.tsx`, `DocChainList.tsx`, `styles.css`(R11-A 블록) | 견적서·주문서 입력 실물화 |
| **클라B** (회계 입력) | `client/src/screens/ReceiptScreen.tsx`, `PaymentScreen.tsx`, `GlEntryScreen.tsx`, **신규** `AcctVoucherEntry.tsx`, `menus.tsx`, `types.ts`, `styles.css`(R11-B 블록) | 회계 입력 5폼 + 메뉴 트리 |

**겹침 규칙**
- A와 B가 함께 건드리는 파일은 `styles.css` **하나뿐**이며, 서로 다른 append 블록(R11-A / R11-B)만 추가한다.
- **B는 A 파일(`DocChainScreen`/`DocChainList`)을 import 금지.** B의 신규 폼은 `VoucherForm`도 import하지 않는다
  (VoucherForm은 A의 견적/주문 + 기존 판매/구매가 공유 → 건드리면 판매입력 R6 패턴이 흔들림).
  B 폼은 `GlEntryScreen`이 이미 하는 방식대로 `voucher-head`/`voucher-lines`/`form-grid` 등 **CSS 클래스만** 직접 조립한다.
- `menus.tsx`(B 소유)는 레지스트리이므로 A 화면(`QuoteList`/`OrderList`)을 import한다 — 이는 기존 패턴이며 허용.
  **A 트리(§12.1·12.2)·B 트리(§12.3~12.7)의 menus.tsx 반영은 전부 B가 수행**한다(두 에이전트가 menus.tsx를 동시 편집하지 않게).
- **VoucherForm.tsx는 R11에서 수정하지 않는다**(기존 슬롯만 활용).

## 2. 서버 재사용 계약 (신규 API 0)

R11 입력폼은 아래 **기존 엔드포인트**로만 저장한다. 모든 폼은 클라이언트에서 payload를 조립해 POST한다.

### 2.1 견적/주문 — `POST /api/docs`, `PUT /api/docs/:id` (vouchers.mjs)
- `type: 'quote'|'order'`, `io_date`, `partner_id`, `warehouse_id`, `tax_mode`, `memo`, `lines[]`, (order) `time_date`, `source_doc_id?`.
- 서버가 금액·`doc_no`·`status`('대기')를 재계산/재채번. quote/order는 원장 미발생(DOC_EMITS_LEDGER 제외) → warnings 항상 `[]`.
- 견적→주문 끌어오기: 기존 `GET /api/docs/pullable?target=order&partner_id=` + `PullSourceModal`(이미 DocChainScreen에 연결됨) 재사용.

### 2.2 매출처로부터 / 매입처로 — `POST /api/receipts` (receipts.mjs)
- body: `{ kind:'수금'|'지불', io_date, partner_id, method, amount, project_id:null, memo }`.
- 저장 트랜잭션 안에서 `writeJournalForReceipt`가 분개 자동 생성:
  - 수금: (차) 현금/보통예금 · (대) 외상매출금[거래처]
  - 지불: (차) 외상매입금[거래처] · (대) 현금/보통예금
- **입금/출금계좌 → method 매핑**: 선택 계정코드 `101`(현금)→`'현금'`, 그 외→`'보통예금'`.
- **수수료**: receipt 스키마에 컬럼이 없다 → 수수료(>0)는 `memo`에 `" (수수료 N원)"`로 덧붙여 기록.
  별도 분개가 필요하면 지출결의서/전표 입력을 쓰라는 field-hint를 단다. (신규 컬럼·API 금지 준수)

### 2.3 지출결의서 / 매출전표Ⅰ / 매입전표Ⅰ — `POST /api/gl-entries` (gl.mjs)
- body: `{ io_date, summary, lines:[{ account_code, dr, cr, partner_id, remarks }] }`.
- gl-entries는 **차변합계=대변합계 강제**(불일치 시 400), 각 라인 계정 존재 검증, `entry_type='일반'`으로 journal 기록.
  → 분개장·거래처원장(외상매출/매입금 라인의 partner_id로 매출/매입 side 자동판정)·전표조회에 자동 합류.
- 클라이언트가 **균형 잡힌 분개 라인**을 만들어 보낸다(아래 §5 매핑표). 계정코드는 005 시딩 상수를 사용.

### 2.4 참조: 005 시딩 계정코드 (자동분개/폼이 참조하는 유일 매핑)
`101 현금` · `103 보통예금` · `108 외상매출금` · `135 부가세대급금` · `153 원재료` ·
`251 외상매입금` · `255 부가세예수금` · `404 제품매출` · `831 지급수수료`(is_system=0, 존재 확인).
사용자 선택 계정은 `GET /api/accounts?active=1&q=`(CodeHelp) 재사용.

## 3. 클라A — 견적서·주문서 입력 실물화

### 3.1 접근 방식
`DocChainScreen`은 이미 공용 `VoucherForm`을 쓴다. **VoucherForm을 수정하지 않고** 기존 3개 슬롯으로 §12.1·12.2를 재현한다:
- `headerExtra` → vh-fields 안에 추가 헤더 필드(유효기간·결제조건·참조·첨부·(주문)납기일자·검색창내용).
- `headerActions` → 라인 그리드 위 툴바(`.line-toolbar`): §12 실물 툴바 버튼들(대부분 동작 없는 stub).
- `footerActions` → 하단 버튼바(저장 우측): ✈ / 저장·전표(F7) / 다시작성 / 리스트 / 웹자료올리기.

> VoucherForm이 렌더하는 기본 저장 버튼은 `저장(F8)`(파랑) 그대로 사용. 실물의 ✈ 최좌측·저장 스플릿(▲) 미세 배치는
> 공용 컴포넌트 보호를 위해 **의도적 미세 편차**로 남긴다(fidelity 80% 목표 내). 하단바 나머지는 footerActions로 채운다.

### 3.2 견적서입력 (§12.1) — `QuoteInput`(DocChainScreen `kind='quote'`)
- **headerExtra 필드**(모두 UI 상태만, 서버 미전송 — quote 스키마에 없음):
  - 통화(`[내자]` disabled) / 참조(input) / 결제조건(input) / 유효기간(`type=date`) / 첨부(`[+]` 버튼 stub).
  - 값은 컴포넌트 state로 보관하되 save payload엔 넣지 않는다(연속입력 시 리셋). field에 `title="참고용(저장 미반영)"`.
- **headerActions 툴바(§12.1 순서)**: `찾기(F3)` `정렬` `거래내역보기(견적)▲` `My품목▲` `할인` `재고불러오기`
  `생성한전표` `바코드` `검증` `이익계산` `전표불러오기` — 전부 stub(`btn small` disabled + title "연동 예정입니다").
  가로 넘침 대비 `.r11a-toolbar`(overflow-x:auto) 래퍼.
- **footerActions**: `✈`(stub) · `저장/전표(F7)`(stub) · `다시작성`(헤더+라인 초기화 — 실동작) · `리스트`(→`onCancel`) · `웹자료올리기`(stub).
  수정모드는 기존대로 `목록으로`/`인쇄`/`삭제` 유지.
- **트리(§12.1)**: 견적서 = 견적서조회·견적서입력·견적서현황·미주문현황 → §4.4 메뉴표 참조(B가 반영).

### 3.3 주문서입력 (§12.2) — `OrderInput`(DocChainScreen `kind='order'`)
- 3.2와 동일 골격 + 주문 전용:
  - **상단 [생산입고 ▼] 파랑 버튼**: 주문→생산입고 연계. 현재 order→roast/생산입고 체인 로직 없음 →
    **stub**(`btn r8-primary` disabled, title "생산입고 연계는 연동 예정입니다"). headerActions 맨 앞에 배치.
  - **headerExtra**: 납기일자(기본 당일, 기존 timeDate 실동작 유지) / 검색창내용(input, UI만) / 참조 / 결제조건 / 첨부(+).
  - 툴바에 `견적`(견적 불러오기) 추가 = **실동작**(기존 `setPullOpen(true)`+`PullSourceModal` 재사용). 나머지 툴바는 stub.
- **트리(§12.2)**: 주문서 = 주문서조회·주문서입력·주문서현황·주문서출고처리·미판매현황 → §4.4 참조.

## 4. 클라B — 회계 입력 실물화

모든 폼은 §2 재사용 계약으로만 저장. 신규 폼은 `VoucherForm` 대신 CSS 클래스로 직접 조립(GlEntryScreen 패턴).

### 4.1 매출처로부터 / 매입처로 (§12.5) — 단순 입출금 폼
- **위치**: `FromSalePartnerInput` → `ReceiptScreen.tsx`에 export 추가 / `ToPurchasePartnerInput` → `PaymentScreen.tsx`에 export 추가
  (두 파일은 이미 `POST /api/receipts`를 쓰므로 저장 로직 재사용에 최적).
- **레이아웃**: `voucher-head` + `vh-fields`(2열) 헤더형 폼(그리드 없음). 필드(§12.5):
  전표일자(`DateParts`류 or `type=date`) / **입금계좌(출금계좌)**(CodeHelp `/api/accounts`) / 거래처(CodeHelp `/api/partners`) /
  금액(number, 우측정렬) / 수수료(number) / 적요(input) / 첨부(`[+]` stub).
- **저장**: `POST /api/receipts`
  - 매출처로부터 → `{ kind:'수금', io_date, partner_id, method:mapAcct(입금계좌), amount, project_id:null, memo }`
  - 매입처로 → `{ kind:'지불', ... method:mapAcct(출금계좌) ... }`
  - `mapAcct(code)= code==='101' ? '현금' : '보통예금'`. 수수료>0이면 memo에 `" (수수료 N원)"` 추가.
- **하단바(§12.5)**: `✈`(stub) `저장(F8)▲`(파랑, 실동작) `저장/전표(F7)▲`(stub) `다시작성`(초기화) `리스트`(stub/토스트).
  검증: 거래처·금액(>0) 필수. 성공 시 토스트 `전표 {receipt_no} 저장` + 폼 리셋.

### 4.2 지출결의서 (§12.6) — 다행 그리드 폼

- **툴바(§12.6)**: `찾기(F3)` `보류` `자금계획` `계좌입출금내역` `카드매입내역` `계정별잔액` — 전부 stub.


## 5. 저장 매핑표 (분개 라인 조립 — gl-entries)

계정코드는 §2.4 상수. 사용자가 계정을 바꾸면 그 코드를 사용, 미변경 시 아래 기본값.

### 5.1 매출전표Ⅰ / 매입전표Ⅰ (§4.3)
`total = 공급가액 + 부가세`, `fee = 수수료`.

**매출전표Ⅰ** (`side='매출'`, 기본 매출계정=404, 입금계좌=108):
| line | account_code | dr | cr | partner_id |
|---|---|---|---|---|
| 입금계좌 | 108(기본) | `total - fee` | 0 | 거래처 |
| 지급수수료(fee>0) | 831 | `fee` | 0 | — |
| 매출계정 | 404(기본) | 0 | `공급가액` | — |
| 부가세예수금(부가세>0) | 255 | 0 | `부가세` | — |

**매입전표Ⅰ** (`side='매입'`, 기본 매입계정=153, 출금계좌=251):
| line | account_code | dr | cr | partner_id |
|---|---|---|---|---|
| 매입계정 | 153(기본) | `공급가액` | 0 | — |
| 부가세대급금(부가세>0) | 135 | `부가세` | 0 | — |
| 지급수수료(fee>0) | 831 | `fee` | 0 | — |
| 출금계좌 | 251(기본) | 0 | `total + fee` | 거래처 |

차합=대합 성립(매출: `total-fee+fee` = `공급가액+부가세`; 매입: `공급가액+부가세+fee` = `total+fee`).
`partner_id`는 채권/채무 계정 라인(108/251)에 세팅 → 거래처원장 자동 판정 + journal head partner 세팅.

### 5.2 지출결의서 (§4.2) — 유효행별 반복
행 = `{ 출금계좌 s, 계정 a, 거래처 p?, 금액 m, 수수료 f, 적요 r }`:
| line | account_code | dr | cr | partner_id | remarks |
|---|---|---|---|---|---|
| 비용/계정 | `a` | `m` | 0 | `p` | `r` |
| 지급수수료(f>0) | 831 | `f` | 0 | — | `r` |
| 출금계좌 | `s` | 0 | `m + f` | — | `r` |
행별 차=대 → 전체 차합=대합. `summary`=헤더 첨언내용.

### 5.3 매출처로부터/매입처로 (§4.1) — receipts (분개는 서버 자동)
클라는 `POST /api/receipts`만 호출. 서버 `writeJournalForReceipt`가 §2.2 2줄 분개를 자동 생성.
