# 설계 — R4 세무 + 회계Ⅱ (100% 완성 플랜)

> 승인 플랜(`/root/.claude/plans/100-dazzling-pnueli.md`) R4 라운드 상세 설계. 문서 형식은 `docs/설계-R3-IA재편성.md`를 따른다.
> **범위 6가지** — 세무: ① 부가가치세신고서 ② 세금계산서합계표 ③ 전자세금계산서(진행단계). 회계Ⅱ: ④ 고정자산등록/감가상각 ⑤ 예산관리 ⑥ 예적금현황·자금계획.
> **사용자 확정 방침**: "구현해놓고 지금은 (외부 전송) 기능만 안되게, 나중에 국세청 API 연동해서 자동으로 연결." → 화면·데이터·계산은 전부 로컬로 동작하고, **외부 전송 버튼([국세청 전송]/[전자발행 전송])만 '연동 예정' 비활성 stub + 코드 TODO 주석**.
> **불변식**: 기존 62개 메뉴 **id 전부 동결**(R3에서 사원등록 신규 1개 포함 62). 신규 메뉴만 새 id. 마이그레이션 번호 **008**(007_employee까지 사용됨). R5=009 선점 유지.
> **핵심 소스 일치**: 부가세신고서·세금계산서합계표의 모든 숫자는 **매입매출장(VatBook, `accounting.mjs:372-419`)과 동일하게 `doc` 테이블(total_supply/total_vat/total_amount)에서 집계**한다(§3.1 소스 일치 근거). journal에서 다시 집계하지 않는다 → 두 화면 숫자가 구조적으로 항상 일치.
> **파일 겹침 0**: 서버 소넷 = **신규 `server/tax.mjs`·`server/assets.mjs` + `server/migrations/008_tax_assets.sql` + `server/index.mjs`(import 2줄·route 2줄)만**. 클라 소넷 = **신규 화면 7파일 + `menus.tsx` + `types.ts` + `styles.css`(append-only)만**. `masters.mjs`·`accounting.mjs`·`App.tsx`·`reportDefs.ts`·`ReportScreen.tsx`는 **무수정**(§0 교집합표).

### 1.2 대메뉴별 집계 (R4 반영 후)

| 대메뉴 | R3 종료 시 | R4 신규 | R4 종료 시 |
|---|---|---|---|
| 세무 | 0 (예약) | +2 (`vat-return`,`tax-invoice-report`) | **2** |
| 회계Ⅰ | 11 | +1 (`e-tax-invoice`) | **12** |
| 회계Ⅱ | 1 (`cash`) | +4 (`fixed-asset`,`budget`,`deposit`,`fund-plan`) | **5** |

- **세무 그룹 활성화**: R3에서 세무는 소속 0개라 대메뉴 바에서 `reserved`(dim·클릭 no-op, App.tsx:117-119)였다. R4가 `vat-return`을 넣으면 `MENUS.find(x=>x.group==='세무')`가 값을 반환 → **App.tsx 무수정으로 자동 활성**. 관리 그룹만 R5까지 `reserved` 유지.
- **회계Ⅱ 채움**: R3에서 `cash`(자금현황) 1개뿐이던 회계Ⅱ에 4개 추가.

## 2. 마이그레이션 008 전체 SQL (deliverable ②)

`server/migrations/008_tax_assets.sql` — `db.mjs`의 `migrate()`가 파일명 오름차순으로 007 다음에 1회 적용. **ALTER 없이 CREATE만** 하므로 004/006 같은 테이블 재빌드 리스크 없음(기존 테이블 무변경).

```sql
-- 008: 세무(전자세금계산서 진행단계) + 회계Ⅱ(고정자산·예산·예적금·자금계획)  [R4]
-- 규칙(001/005와 동일): 금액 INTEGER(원), 수량/율 REAL, 코드/이름 UNIQUE, active로 사용여부.
-- 전부 신규 테이블 CREATE만 한다(기존 doc/journal/account 등 무변경). 부가세신고서·세금계산서합계표는
-- 신규 테이블이 필요 없다 — 기존 doc 집계이므로 여기에 테이블을 만들지 않는다(§3.1 소스 일치).

-- ── ① 전자세금계산서 진행단계(판매 전표 1건 = 상태 1건, 없으면 '미발행'으로 간주) ──
-- 대장은 doc(sale) LEFT JOIN 으로 생성하고, 상태 변경 시에만 이 표에 upsert 한다(미발행 행은 저장 안 함).
-- 원천 판매 전표 삭제 시 ON DELETE CASCADE로 상태도 정리된다(분개/재고원장과 동일한 파생 성격).
CREATE TABLE tax_invoice_status (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  doc_id INTEGER NOT NULL UNIQUE REFERENCES doc(id) ON DELETE CASCADE,  -- 원천 판매 전표(1:1)
  status TEXT NOT NULL DEFAULT '미발행'
    CHECK (status IN ('미발행','발행','전송예정','전송완료')),           -- 전송완료는 국세청 연동(연동 예정)으로만 도달
  issued_at TEXT,                                  -- 발행 처리 일시(로컬). '발행' 전환 시 기록
  sent_at TEXT,                                    -- 국세청 전송완료 일시(연동 예정 — 현재 항상 NULL)
  approval_no TEXT NOT NULL DEFAULT '',            -- 국세청 승인번호 24자리(연동 예정 — 현재 빈값)
  memo TEXT NOT NULL DEFAULT '',
  updated_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX idx_taxinv_doc ON tax_invoice_status (doc_id);

-- ── ② 고정자산(정액법 감가상각) ──
-- 감가상각 스케줄은 저장하지 않는다 — acq_date/acq_cost/salvage_value/life_years로 서버가 계산(§3.3).
CREATE TABLE fixed_asset (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code TEXT NOT NULL UNIQUE,                        -- 자산코드
  name TEXT NOT NULL,                               -- 자산명
  asset_account TEXT NOT NULL DEFAULT '비품',        -- 자산계정(건물/기계장치/차량운반구/비품/무형자산 등)
  acq_date TEXT NOT NULL,                           -- 취득일 'YYYY-MM-DD'
  acq_cost INTEGER NOT NULL DEFAULT 0,              -- 취득가액(원)
  salvage_value INTEGER NOT NULL DEFAULT 0,         -- 잔존가치(원)
  life_years INTEGER NOT NULL DEFAULT 5,            -- 내용연수(년). 월상각 기준 = life_years*12 개월
  method TEXT NOT NULL DEFAULT '정액법'
    CHECK (method IN ('정액법')),                    -- R4는 정액법만(정률법은 범위 밖)
  memo TEXT NOT NULL DEFAULT '',
  active INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

-- ── ③ 예산(계정과목 × 연 × 월 편성액) ──
CREATE TABLE budget (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  fiscal_year INTEGER NOT NULL,                     -- 회계연도 예: 2026
  month INTEGER NOT NULL CHECK (month BETWEEN 1 AND 12),
  account_code TEXT NOT NULL REFERENCES account(code),  -- 계정과목(account.code는 UNIQUE)
  amount INTEGER NOT NULL DEFAULT 0,                -- 편성 예산액(원)
  memo TEXT NOT NULL DEFAULT '',
  UNIQUE (fiscal_year, account_code, month)
);
CREATE INDEX idx_budget_year ON budget (fiscal_year, account_code);

-- ── ④ 예적금(수기 등록) ──
CREATE TABLE deposit (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code TEXT NOT NULL UNIQUE,                        -- 관리코드
  name TEXT NOT NULL,                               -- 예적금명(상품명)
  bank TEXT NOT NULL DEFAULT '',                    -- 금융기관(은행)
  account_no TEXT NOT NULL DEFAULT '',              -- 계좌번호
  kind TEXT NOT NULL DEFAULT '예금'
    CHECK (kind IN ('예금','적금')),
  principal INTEGER NOT NULL DEFAULT 0,             -- 원금/현재잔액(원)
  rate REAL NOT NULL DEFAULT 0,                     -- 연이율(%)
  start_date TEXT NOT NULL DEFAULT '',              -- 가입일 'YYYY-MM-DD'
  maturity_date TEXT NOT NULL DEFAULT '',           -- 만기일 'YYYY-MM-DD'
  memo TEXT NOT NULL DEFAULT '',
  active INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

-- ── ⑤ 자금계획(월별 예정 수입/지출) ──
CREATE TABLE fund_plan (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  plan_date TEXT NOT NULL,                          -- 예정일자 'YYYY-MM-DD'
  flow TEXT NOT NULL DEFAULT '수입'
    CHECK (flow IN ('수입','지출')),
  amount INTEGER NOT NULL DEFAULT 0,                -- 금액(원)
  partner_id INTEGER REFERENCES partner(id),        -- 거래처(선택)
  title TEXT NOT NULL DEFAULT '',                   -- 내용/적요
  memo TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX idx_fundplan_date ON fund_plan (plan_date);
```

**테이블 목록**: `tax_invoice_status` · `fixed_asset` · `budget` · `deposit` · `fund_plan` (5).

**DDL 사전검증 절차**(서버 소넷 필수): `data/erp.sqlite` 사본에 `foreign_keys=ON`으로 008 적용 → 5테이블 생성·`PRAGMA foreign_key_check` 0건 확인 → `tax_invoice_status(doc_id=<존재 sale>)` upsert OK, `doc_id=9999`(미존재) FK 거부 확인 → 사본 폐기(§5.1).

## 3. 서버 API 명세 (deliverable ③)

공용 헬퍼는 기존 `server/ledger.mjs`(err/readBody/friendlySqlError/isValidDate/todayISO/validId/round1)를 import 재사용. 기간 기본값 `monthStartISO()`는 각 파일 상단에 로컬 복제(accounting/finreports/cash와 동일 관례).

### 3.1 부가가치세신고서 — `GET /api/vat-return` (tax.mjs)

**요청**: `?from=YYYY-MM-DD&to=YYYY-MM-DD`. 기본값 = 이번달 1일~오늘. 과세기간 프리셋은 클라가 from/to로 변환해 보냄(§4.1).

**소스 일치 근거(★핵심)**: 아래 두 쿼리는 매입매출장(`accounting.mjs:382-388`의 `docs` 조회 + `summarize()`)과 **완전히 동일한 원천·필터·컬럼**을 사용한다 — `doc` 테이블, `doc_type IN('sale'/'purchase')`, `io_date BETWEEN`, `tax_mode`로 과세/면세 분리, 금액은 `total_supply`/`total_vat`(캐시 컬럼). journal은 쓰지 않는다. 따라서 **부가세신고서 과세표준 = VatBook `summary.매출.과세공급`, 매출세액 = `summary.매출.부가세`, 매입세액 = `summary.매입.부가세`** 가 항상 성립(같은 SQL, 같은 반올림 캐시값).

```sql
-- 매출 집계
SELECT tax_mode,
       COALESCE(SUM(total_supply),0) AS supply,
       COALESCE(SUM(total_vat),0)    AS vat,
       COUNT(*)                       AS cnt
FROM doc
WHERE doc_type='sale' AND io_date>=? AND io_date<=?
GROUP BY tax_mode;
-- 매입 집계 (doc_type='purchase'로 동일 쿼리 1회 더)
```

JS 조립(과세=tax_mode '과세', 면세='면세'):
```js

const sFree = salesRows.find(r=>r.tax_mode==='면세') ?? {supply:0,vat:0,cnt:0};
const pTax = purRows.find(r=>r.tax_mode==='과세') ?? {supply:0,vat:0,cnt:0};

const sales_vat  = sTax.vat;                 // 매출세액
const purchase_vat = pTax.vat;               // 매입세액
```

- 회사정보는 `SELECT key,value FROM settings WHERE key IN('company_name','company_biz_no','company_ceo')`로 채운다(PnlStatement/StatementSheet와 동일).
- **엣지케이스**: ① **빈 기간**(전표 0건) → 모든 값 0, `payable=0`, 200 정상(에러 아님). ② **면세 거래만** → `tax_base=0`, `sales_vat=0`, `free_supply>0`(면세 수입금액 라인에만 표시). ③ **매입세액 > 매출세액** → `payable` 음수 = 환급세액(클라가 '환급'으로 표기). ④ `from>to` → 집계 0(에러 아님). ⑤ 영세율(0%): 현 데이터 모델은 `tax_mode`가 과세/면세뿐이라 영세율 라인은 항상 0(신고서 서식에 자리만 두고 0 표기, 코드 TODO).

### 3.2 세금계산서합계표 — `GET /api/tax-invoice-report` (tax.mjs)

**요청**: `?from&to`. 기본 이번달.

세금계산서 = **과세 거래**(`tax_mode='과세'`)만 대상(면세는 계산서합계표로 별도 — R4 범위 밖, 서식에 '계산서' 자리만 0). 거래처(사업자번호)별 **매수(전표 건수)·공급가액·세액** 집계, 매출/매입 각각.

```sql
-- side ∈ {sale, purchase} 각각 1회
SELECT d.partner_id, p.name AS partner_name, COALESCE(p.biz_no,'') AS biz_no,
       COUNT(*)                       AS sheet_count,   -- 매수(세금계산서 건수 = 전표 건수)
       COALESCE(SUM(d.total_supply),0) AS supply,
       COALESCE(SUM(d.total_vat),0)    AS vat
FROM doc d LEFT JOIN partner p ON p.id=d.partner_id
WHERE d.doc_type=? AND d.tax_mode='과세' AND d.io_date>=? AND d.io_date<=?
GROUP BY d.partner_id
ORDER BY p.name;
```

**응답**:
```jsonc
{
  "from":"2026-04-01","to":"2026-06-30","company_name":"빈스로스터스","company_biz_no":"123-45-67890",
  "sales": {
    "rows": [
      { "partner_id":3, "partner_name":"블루보틀상봉", "biz_no":"111-22-33333",
        "sheet_count":5, "supply":3000000, "vat":300000 }

    "totals": { "partner_count":8, "sheet_count":34, "supply":12000000, "vat":1200000 }

```
- `totals.partner_count` = 거래처 수(rows.length), `sheet_count` = 매수 합, supply/vat = 합.
- **엣지케이스**: ① 거래처 미지정(`partner_id IS NULL`) → `partner_name='(거래처 미지정)'`, `biz_no=''`로 1행. ② 면세 거래는 rows에서 제외(합계에도 미포함) — 세금계산서 대상 아님. ③ 빈 기간 → rows=[], totals 전부 0. ④ 같은 거래처 여러 전표 → 1행으로 GROUP(매수만 증가).

### 3.3 전자세금계산서 진행단계 — `GET/PUT /api/tax-invoices` (tax.mjs)

전자세금계산서는 **판매 과세 전표**를 대상으로 한 발행상태 대장. 상태는 `tax_invoice_status` 테이블에 기록하되, **미발행은 저장하지 않고 LEFT JOIN 시 COALESCE로 간주**(대장이 판매전표를 항상 전량 표시).

**GET `/api/tax-invoices?from&to&status`** (status 선택: 미발행/발행/전송예정/전송완료/전체)
```sql
SELECT d.id AS doc_id, d.doc_no, d.io_date, d.tax_mode,
       d.total_supply, d.total_vat, d.total_amount,
       p.name AS partner_name, COALESCE(p.biz_no,'') AS biz_no,
       COALESCE(t.status,'미발행') AS status, t.issued_at, t.approval_no, t.memo
FROM doc d
LEFT JOIN partner p ON p.id=d.partner_id
LEFT JOIN tax_invoice_status t ON t.doc_id=d.id
WHERE d.doc_type='sale' AND d.tax_mode='과세' AND d.io_date>=? AND d.io_date<=?
  -- status 필터 시: AND COALESCE(t.status,'미발행')=?
ORDER BY d.io_date DESC, d.id DESC;
```
+ 각 행 `item_summary`(첫 품목명 `외 N건` — accounting.mjs `lineNames` 서브쿼리 복제).

### 3.4 고정자산 + 감가상각(정액법) — `/api/fixed-assets*`, `/api/depreciation` (assets.mjs)

**마스터 CRUD**(masters.mjs 무수정 → assets.mjs 내부에 격리 복제한 `crud()` 헬퍼로 생성):
| 메서드 | 경로 | 동작 |
|---|---|---|
| GET | `/api/fixed-assets?q=` | code/name LIKE 검색, `ORDER BY code`. `SELECT *` |
| POST | `/api/fixed-assets` | code·name 필수, acq_date isValidDate, life_years≥1·acq_cost≥0·salvage_value≥0 검증. UNIQUE 위반 → 친절 메시지 |
| PUT | `/api/fixed-assets/:id` | 화이트리스트 컬럼 갱신 |
| DELETE | `/api/fixed-assets/:id` | 삭제(참조 없음 — 스케줄은 파생 계산이라 FK 없음) |

> `crud(route, table, cols, required, label)` 헬퍼 = masters.mjs의 for-루프 본문(GET/POST/PUT/DELETE + readBody/friendlySqlError)을 assets.mjs 안에 그대로 복제. `fixed-assets`·`deposits` 두 곳에서 호출. **masters.mjs는 손대지 않는다**(파일 격리 규칙).

**정액법 월별 스케줄 계산**(순수 함수, 저장 안 함):
```js
// 월상각 기준액 = 취득가액 - 잔존가치. 총 개월수 = life_years*12.
// 월상각액 = round(기준액 / 총개월). 취득월(acq_date의 YYYY-MM)부터 상각 시작(월할, 일할 아님).
// 마지막 달은 (기준액 - 직전까지 누계)로 보정 → 총상각 = 기준액 정확히 일치(반올림 잔차 흡수).
function schedule(a) {
  const base = Math.max(0, a.acq_cost - a.salvage_value);
  const n = Math.max(1, a.life_years * 12);
  const per = Math.round(base / n);
  const rows = [];
  let accum = 0;
  let [y, m] = a.acq_date.slice(0,7).split('-').map(Number);
  for (let i = 0; i < n; i++) {
    const dep = (i === n - 1) ? (base - accum) : per;  // 마지막 달 보정
    accum += dep;
    rows.push({ ym: `${y}-${String(m).padStart(2,'0')}`, dep,
                accum, book_value: a.acq_cost - accum });  // book_value ≥ salvage_value
    m++; if (m > 12) { m = 1; y++; }
  }
  return rows;  // 길이 = life_years*12
}
```
- **GET `/api/fixed-assets/:id/schedule`** → `{ asset:{...}, monthly_dep, total_dep, rows:[{ym,dep,accum,book_value}] }`.
- **GET `/api/depreciation?from&to&asset_id?`** → 기간 내 월별/자산별 상각 현황.
  - `by_asset`: 활성 자산별 `{ code,name,asset_account,acq_date,acq_cost,salvage_value,monthly_dep, dep_in_range(기간 내 상각 합), accum_to(to까지 누계), book_value(to 시점 미상각잔액) }`.
  - `by_month`: 기간 내 각 월 `{ ym, dep(전 자산 합) }`.
  - `totals`: `{ asset_count, dep_in_range, accum_to }`.
  - 계산: 각 자산 `schedule()`을 만들고 `ym`이 `[from,to]` 월 범위에 드는 행만 합산(상각 종료 후 월은 dep 없음).

**엣지케이스**:
- **잔존가치 0** → base=acq_cost, 만기 시 book_value=0.
- **월 중 취득**(예: 취득일 06-15) → 06월부터 만액 상각(월할, 취득월 포함). 일할 안 함 — 문서에 명시된 R4 규칙.
- **잔존가치 ≥ 취득가액**(또는 base=0) → 월상각 0, 스케줄 전부 dep=0(book_value=acq_cost 고정). 에러 아님.
- **life_years 미입력/0** → `Math.max(1,…)`로 최소 1년 방어(POST에서 life_years≥1 검증도 병행).
- **상각 완료 자산**(경과월 ≥ n) → `by_asset.dep_in_range=0`, `book_value=salvage_value`, `accum_to=base`.
- **조회 기간이 취득 전** → 해당 자산 dep_in_range=0(현황엔 표시하되 0).
- **범위 밖(문서 명시)**: 감가상각 **자동분개는 만들지 않는다**(조회·계산까지만). 이카운트의 FastEntry 감가상각전표는 R6+ 후보. `assets.mjs`에 `// TODO: 감가상각비/감가상각누계액 자동분개는 R4 범위 밖(조회·계산만).` 주석.

### 3.5 예산관리 — `GET/PUT /api/budget` (assets.mjs)

**GET `/api/budget?year=2026`**: 계정별 12개월 편성액 + 실적(journal 집계) + 대비.
```sql
-- 편성액
SELECT account_code, month, amount FROM budget WHERE fiscal_year=?;
-- 실적(전 계정·전월 한 번에)
SELECT jl.account_code, substr(j.io_date,1,7) AS ym,
       COALESCE(SUM(jl.dr),0) AS dr, COALESCE(SUM(jl.cr),0) AS cr
FROM journal_line jl JOIN journal j ON j.id=jl.journal_id
WHERE substr(j.io_date,1,4)=?
GROUP BY jl.account_code, ym;
```
- 실적 방향: `account.category`가 차변성(자산·비용)이면 월 실적 = `dr-cr`, 대변성(부채·자본·수익)이면 `cr-dr`. (finreports.mjs `DR_CATEGORIES`와 동일 규칙.)
- **대상 계정**: `category='비용'`인 활성 계정 ∪ 해당 연도 budget 행이 있는 계정(예산 편성 대상 = 비용 위주지만, 수익도 편성했으면 표시). `ORDER BY code`.

**응답**:
```jsonc
{
  "year": 2026,
  "rows": [
    { "account_code":"811", "account_name":"복리후생비", "category":"비용",
      "budget":[100000,100000, ... 12개], "actual":[80000,120000, ... 12개],
      "budget_total":1200000, "actual_total":1150000,
      "variance": 50000,         // 편성 - 실적(잔액)
      "rate_pct": 96             // 집행률 = round(actual_total/budget_total*100), budget 0이면 0
    }
  ],
  "totals": { "budget_total": ..., "actual_total": ..., "variance": ..., "rate_pct": ... }
}
```

**PUT `/api/budget`** — 편성액 저장(bulk upsert). body `{ fiscal_year, entries:[{account_code, month, amount}] }`.
```sql
INSERT INTO budget (fiscal_year, account_code, month, amount)
VALUES (?,?,?,?)
ON CONFLICT(fiscal_year, account_code, month) DO UPDATE SET amount=excluded.amount;
-- amount=0 인 entry는 기존행 삭제(빈 셀 유지) 하거나 0 저장 — 0 저장으로 단순화.
```
- 트랜잭션 1회로 전 entries upsert(masters.mjs `/settings` PUT과 동일 패턴). `account_code`가 account에 없으면 FK 거부(friendlySqlError).

**엣지케이스**: ① 예산 미편성 계정 → `budget` 전부 0, `rate_pct=0`(0으로 나눗셈 방어). ② 실적만 있고 예산 0 → variance 음수(초과), rate_pct=0 표기(분모 0). ③ 자동분개 실적: 판매/구매 자동분개는 비용 8xx 계정을 만들지 않으므로 **비용 예산 실적은 일반전표(gl-entry, entry_type='일반')로만 발생** — 월별손익/손익계산서의 판관비와 동일 소스(정합). ④ 연도 경계: `substr(io_date,1,4)` 문자열 비교.

**검증 지점**: 특정 계정·월 실적값 = 분개장(`GET /api/journal?account_code=&from=&to=`)의 해당 월 `Σ(dr-cr)`(차변성) 과 일치(§5.2).

## 5. 소넷 자가 검증 시나리오 (deliverable ⑤)

### 5.1 테스트 데이터·DB 사본 규칙 (doc_seq 원복 포함)

- **원칙: 집계 검증은 실 DB의 기존 전표에 대해 읽기전용으로**(부가세신고서·합계표·전자세금계산서 GET·감가상각·예산 실적 GET은 전부 SELECT — doc_seq·원장 무변경).
- **쓰기가 필요한 검증은 사본 DB에서**: `cp data/erp.sqlite /tmp/erp-r4-test.sqlite` → 사본을 열어 008 적용·CRUD·PUT 검증 → **사본 폐기**(원본 무변경). R3 검증(설계-R3 §3.1)과 동일 절차.
- **doc_seq 원복 규칙**(부득이 실 DB에 판매전표를 넣어 부가세 대조할 경우): `nextSeqNo`는 삭제해도 감소하지 않으므로, 테스트 전표 k건 삭제 후 반드시
  `UPDATE doc_seq SET last_no = last_no - <k> WHERE io_date='<YYYYMMDD>' AND seq_key='sale';`
  로 되돌린다(그 (일자,유형)에 실 전표가 없을 때만 안전). **권장은 사본 DB 사용 → doc_seq 원복 불필요.**
- R4 신규 5테이블은 doc_seq를 쓰지 않는다(자체 AUTOINCREMENT) → 신규 테이블 CRUD 테스트는 사본에서 자유롭게 하고 폐기.

### 5.2 수기 대조 필수 항목 (숫자 일치)

1. **부가세신고서 = 매입매출장 합계**(★): 같은 기간으로 `GET /api/vat-return`과 `GET /api/vat-book`를 호출해
   - `vat-return.tax_base` == `vat-book.summary.매출.과세공급`
   - `vat-return.sales_vat` == `vat-book.summary.매출.부가세`
   - `vat-return.purchase_vat` == `vat-book.summary.매입.부가세`
   - `vat-return.payable` == (매출.부가세 − 매입.부가세)
   가 **정확히 일치**함을 확인(같은 doc 집계라 반드시 성립 — 불일치 시 버그).
2. **세금계산서합계표 = 부가세신고서**: `tax-invoice-report.sales.totals.supply` == `vat-return.tax_base`, `.sales.totals.vat` == `vat-return.sales_vat`(둘 다 과세 매출 doc 합).
3. **감가상각 총액 = 수기 계산**: 취득가 A·잔존 S·내용연수 Y년인 자산의 스케줄에서 `Σdep == A−S`(마지막 달 보정으로 정확 일치), 월상각 ≈ `round((A−S)/(Y*12))`, `경과월 m`의 누계 ≈ `min(round((A−S)/(Y*12))*m, A−S)`. 예: A=6,000,000·S=0·Y=5 → 월상각 100,000, 총상각 6,000,000, book_value 만기 0. 월중 취득(06-15)이면 06월부터 상각 시작 확인.
4. **예산 대비 실적 = 분개장 합계**: 임의 비용계정(예 811)·월에 대해 `budget.rows[].actual[m]` == `GET /api/journal?account_code=811&from=<월초>&to=<월말>`의 `Σ(dr−cr)`. 일반전표 1건(811 차변) 추가 후(사본 DB) 실적이 그만큼 증가하는지 확인.
5. **전자세금계산서 상태 왕복**: 사본에서 판매전표 1건에 `PUT /api/tax-invoices/:docId {status:'발행'}` → GET 대장에서 status='발행'·issued_at 기록·`counts` 반영 확인. `status:'전송완료'` PUT → 400 거부 확인. 판매전표 삭제 → CASCADE로 상태 사라짐 확인.

## 6. 리스크 · 결정 메모

- **소스 일치가 R4 정합성의 핵심**: 부가세신고서·합계표를 journal이 아닌 `doc`(VatBook과 동일)에서 집계 → 매입매출장과 항상 일치, 대조 부담 0. journal 기반으로 만들면 자동분개 반올림·계정 매핑 차이로 불일치 위험 → 채택 안 함.
- **미발행 행 비저장**: 전자세금계산서 대장은 `doc LEFT JOIN tax_invoice_status`로 생성 → 판매전표 추가/삭제에 대장이 자동 동기화(백필 불필요), 상태 변경분만 테이블에 남김.
- **감가상각 월할·마지막달 보정**: 월중 취득도 취득월부터 만액(일할 아님), 마지막 달이 반올림 잔차를 흡수해 `Σdep=취득가−잔존` 정확. 자동분개는 범위 밖(조회·계산만) — 사용자 확정 범위 준수.
- **masters.mjs 무수정**: 고정자산·예적금 CRUD를 assets.mjs 내부 `crud()`로 격리 복제 → 서버·클라 파일 겹침 0 규칙과 masters.mjs 안정성 동시 유지.
- **App.tsx 무수정으로 세무 그룹 활성**: R3의 `reserved` 판정이 `MENUS.find(group===g)` 기반이라 메뉴 추가만으로 dim 자동 해제 → R4는 App.tsx를 건드리지 않는다(관리 그룹만 R5까지 예약 유지).
- **외부 연동 일괄 stub**: [국세청 전송]/[전자발행 국세청 전송]은 `.stub-btn` 비활성 + 코드 `// TODO(국세청 연동)` 주석. 로컬 발행상태·집계·인쇄는 완전 동작 → 사용자 확정 방침("지금은 기능만 안되게, 나중에 국세청 API 연동") 그대로 반영.
- **id 동결·마이그레이션 번호**: 기존 62개 id 무변경, 신규 7개만 추가. 008 선점(R5=009 유지). 즐겨찾기(`erp_favorites`) 회귀 없음.
