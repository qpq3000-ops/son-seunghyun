## 0. 코드 컨벤션 (Phase 1~3과 동일 — 재확인)

- **금액**: `INTEGER`(원). 서버가 항상 재계산, 클라 값 신뢰 안 함. `Math.trunc`로 정수화.
- **수량**: `REAL`(kg 소수 1자리). `round1()`(ledger.mjs)로 합산 오차 정리.
- **오류 응답**: `err(c, status, '한국어 메시지')` (ledger.mjs). 클라는 `api`(api.ts)가 서버 한국어 메시지를 그대로 throw → toast.
- **본문 파싱**: `readBody(c)`(배열/비객체는 null). 날짜 검증 `isValidDate`. `:id` 검증 `validId`.
- **트랜잭션**: 쓰기는 `db.transaction(()=>{...})()`. 채번은 트랜잭션 안 `nextSeqNo(ioDate, seqKey)`.
- **조회 화면 기간 기본값**: 이번달 1일 ~ 오늘 (`monthStartISO()`/`todayISO()` — format.ts / 각 서버 파일 로컬 복제).
- **화면 골격**: 흰 테마. `screen > screen-bar(search-group + btn-group) > screen-grid(DataGrid)`. 검색 버튼은 `검색(F3)` 표기 관례. 기간 프리셋이 필요한 화면은 StatementPrint의 `preset()`(금일/전일/금주/전주/금월/전월) 패턴 재사용.
- **파생 원장 원칙**: `stock_ledger`·`journal`은 원천 전표를 재작성하면 트랜잭션 안에서 다시 쓰이는 파생 데이터. 이 원칙의 유일한 예외가 이번 **일반전표**(원천 없는 독립 분개) — 아래 1장 참조.

## 1. 마이그레이션 006 — 일반전표(수동분개) 허용 (실 DB 사본 검증 완료)

### 1.1 배경 · 결정

`005_accounting.sql`의 `journal` 테이블에는 **원천 강제 제약**이 있다:

```sql
CHECK ((doc_id IS NOT NULL) + (receipt_id IS NOT NULL) = 1)   -- 정확히 하나의 원천
entry_type TEXT NOT NULL CHECK (entry_type IN ('매출','매입','수금','지불'))
```

일반전표(경비 등 수동 분개)는 **원천 전표가 없다** → `doc_id`/`receipt_id`가 **둘 다 NULL**이어야 하는데 위 제약이 이를 금지한다. 그리고 `entry_type`에 수동전표 유형이 없다. 따라서 마이그레이션 006이 **필수**다.

SQLite는 `CHECK`/컬럼 목록을 `ALTER`로 바꿀 수 없으므로 `journal` 테이블을 **재빌드**한다(004의 `doc` 재빌드와 동일 패턴). 자식 `journal_line`이 `journal` DROP 시 `ON DELETE CASCADE`로 지워지지 않도록 FK 없는 임시표로 백업했다가 되돌린다. 러너(`db.mjs migrate()`)가 트랜잭션 안에서 실행하므로 원자적이다.

**변경 요지**: 원천 제약을 `= 1`(정확히 1개) → `<= 1`(0개 또는 1개)로 완화하고, `entry_type` 허용값에 `'일반'`을 추가한다.

### 1.2 DDL 전문 — `server/migrations/006_gl_entry.sql`

```sql
-- Phase 3 잔여: 일반전표(수동분개) 허용 — journal의 원천 제약을 '정확히 1개'에서 '0 또는 1개'로 완화 (마이그레이션 006)
-- 규칙(005와 동일): 분개는 파생 원장. 단, 일반전표는 원천 전표가 없는 '독립 분개'다(doc_id/receipt_id 모두 NULL).
-- SQLite는 CHECK/컬럼목록을 ALTER로 못 바꾸므로 journal 테이블을 재빌드한다(004 doc 재빌드와 동일 패턴).
-- 자식(journal_line)이 journal DROP 시 ON DELETE CASCADE로 지워지지 않도록 FK 없는 임시표로 백업했다가 되돌린다.

-- ── ① 자식 백업(FK 없는 임시표) ─────────────────────────────
CREATE TABLE _mig_journal_line AS SELECT * FROM journal_line;
DELETE FROM journal_line;

-- ── ② journal 재빌드(entry_type에 '일반' 추가 + 원천 CHECK를 <=1로 완화) ──
CREATE TABLE journal_new (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  doc_id INTEGER REFERENCES doc(id) ON DELETE CASCADE,           -- 원천이 판매/구매 전표일 때
  receipt_id INTEGER REFERENCES receipt(id) ON DELETE CASCADE,   -- 원천이 수금/지불일 때
  entry_type TEXT NOT NULL
    CHECK (entry_type IN ('매출','매입','수금','지불','일반')),   -- '일반' = 일반전표(수동분개, 경비 등)
  io_date TEXT NOT NULL,
  doc_no TEXT NOT NULL,                       -- 자동분개=원천 전표번호 / 일반전표=doc_seq('gl')로 채번한 'YYYYMMDD-N'
  partner_id INTEGER REFERENCES partner(id),
  summary TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  CHECK ((doc_id IS NOT NULL) + (receipt_id IS NOT NULL) <= 1)   -- 원천은 0개(일반전표) 또는 1개(자동분개)
);

INSERT INTO journal_new (id, doc_id, receipt_id, entry_type, io_date, doc_no, partner_id, summary, created_at)
SELECT id, doc_id, receipt_id, entry_type, io_date, doc_no, partner_id, summary, created_at FROM journal;

DROP TABLE journal;
ALTER TABLE journal_new RENAME TO journal;

-- ── ③ 자식 복원 후 임시표 제거 ─────────────────────────────
INSERT INTO journal_line SELECT * FROM _mig_journal_line;
DROP TABLE _mig_journal_line;

-- ── ④ 인덱스 재생성(옛 journal과 함께 사라진 것) ───────────
CREATE UNIQUE INDEX uq_journal_doc     ON journal (doc_id)     WHERE doc_id IS NOT NULL;
CREATE UNIQUE INDEX uq_journal_receipt ON journal (receipt_id) WHERE receipt_id IS NOT NULL;
CREATE INDEX idx_journal_date    ON journal (io_date);
CREATE INDEX idx_journal_partner ON journal (partner_id);
```

### 1.3 사본 검증 결과 (원본 `data/erp.sqlite`는 미변경)

`data/erp.sqlite` 사본에 기존 자동분개 1건(매출, 라인 3개)을 심고 006을 적용해 확인:

1. **기존 행 보존** — 재빌드 후 journal 1건·journal_line 3건 그대로. 인덱스 4개 재생성 확인.
2. **일반전표 삽입 성공** — `doc_id=NULL, receipt_id=NULL, entry_type='일반'` INSERT 통과(임차료 500,000 차변 / 보통예금 500,000 대변).
3. **차대변 균형은 DB가 강제하지 않음** — `dr=100,cr=0`(불균형) 단일 라인도 DB는 수용 → **균형 검증은 서버(gl.mjs)가 강제**(005 `insertJournal`과 동일 원칙).
4. **자동분개 보호 유지** — 원천(sale doc) 삭제 시 그 자동분개는 CASCADE 삭제되고, **일반전표는 그대로 생존**(원천이 없어 CASCADE 대상 아님).
5. **일반전표 삭제** — `DELETE FROM journal` 시 자식 라인 CASCADE 삭제 정상.
6. **월별손익 자동 합류** — `monthly-pl`의 판관비 집계(`account.category='비용' AND account_code LIKE '8%'`)가 수동 경비(예: 819 임차료) 500,000을 **자동 포착**. 기존 집계 로직 수정 불필요.

> **왜 별도 컬럼/원장을 안 만드나**: 일반전표도 `journal`/`journal_line`에 그대로 들어가므로 분개장·거래처원장·월별손익 등 **journal 기반 집계에 자동 합류**한다. `entry_type='일반'`으로만 구분한다. backfill(`accounting.mjs`)은 `doc_id/receipt_id IS NOT NULL`만 대상이라 일반전표를 절대 건드리지 않는다.

## 2. 데이터 출처 매핑 (7종이 새 테이블 없이 성립함을 확인)

| 메뉴 | 주 출처 | 성격 |
|---|---|---|

### 3.1 로스팅 전표 목록 — `GET /api/roast-docs` (prodquery.mjs) — lot·prod-in 공용

roast 전표 1건 = 배치 로트. lot과 prod-in이 **같은 응답**을 쓰되 표시 컬럼만 다르게 고른다(중복 엔드포인트 방지).

**쿼리**: `from`, `to`(기본 이번달~오늘), `item_id`(선택 — 산출품목 필터).

**참조 구현**:
```js
prodQuery.get('/roast-docs', (c) => {
  const from = isValidDate(c.req.query('from')) ? c.req.query('from') : monthStartISO();
  const to   = isValidDate(c.req.query('to'))   ? c.req.query('to')   : todayISO();
  const itemId = Number(c.req.query('item_id')) || 0;

  let sql = `
    SELECT d.id, d.doc_no, d.io_date, d.warehouse_id, w.name AS warehouse_name,
           d.total_qty AS output_total, d.yield_pct, d.memo,
           (SELECT dl.item_id FROM doc_line dl WHERE dl.doc_id=d.id AND dl.line_role='output' LIMIT 1) AS output_item_id
    FROM doc d JOIN warehouse w ON w.id=d.warehouse_id
    WHERE d.doc_type='roast' AND d.io_date>=? AND d.io_date<=?`;
  const params = [from, to];
  if (itemId) {
    sql += ` AND EXISTS (SELECT 1 FROM doc_line dl WHERE dl.doc_id=d.id AND dl.line_role='output' AND dl.item_id=?)`;
    params.push(itemId);
  }
  sql += ` ORDER BY d.io_date DESC, d.id DESC`;

  const inputStmt = db.prepare(`
    SELECT dl.item_id, i.code AS item_code, i.name AS item_name, dl.qty
    FROM doc_line dl JOIN item i ON i.id=dl.item_id
    WHERE dl.doc_id=? AND dl.line_role='input' ORDER BY dl.line_no`);
  const nameStmt = db.prepare(`SELECT name FROM item WHERE id=?`);

  return c.json(db.prepare(sql).all(...params).map(r => {
    const inputs = inputStmt.all(r.id);
    const input_total = round1(inputs.reduce((s, x) => s + x.qty, 0));
    return {
      ...r,
      output_item_name: r.output_item_id ? (nameStmt.get(r.output_item_id)?.name ?? '') : '',
      inputs,
      input_total,
      input_summary: inputs.map(x => `${x.item_name} ${round1(x.qty)}`).join(', '),
    };
  }));
});
```

### 3.2 소요량계산 — `GET /api/mrp` (prodquery.mjs)

대기 주문(주문서 `doc_type='order'`, `status='대기'`)의 품목별 필요량 → 제품 현재고 차감 → 부족분 → paired 생두 환산 → 생두 현재고 차감 → 생두 부족분.

**쿼리**: 없음(대기 주문 전량 기준). 재고는 오늘 시점 `stock_ledger` 누계(모든 창고 합).

**참조 구현**:
```js
prodQuery.get('/mrp', (c) => {
  const need = db.prepare(`
    SELECT dl.item_id, i.code AS item_code, i.name AS item_name, i.unit,
           i.paired_item_id, i.default_yield, SUM(dl.qty) AS required
    FROM doc_line dl
    JOIN doc d ON d.id=dl.doc_id
    JOIN item i ON i.id=dl.item_id
    WHERE d.doc_type='order' AND d.status='대기'
    GROUP BY dl.item_id, i.code, i.name, i.unit, i.paired_item_id, i.default_yield
    ORDER BY i.code`).all();

  const stockOf = (id) => round1(db.prepare(
    `SELECT COALESCE(SUM(qty),0) AS b FROM stock_ledger WHERE item_id=?`).get(id).b);
  const meta = (id) => db.prepare(`SELECT code, name, unit FROM item WHERE id=?`).get(id);

  const rows = need.map(n => {
    const required = round1(n.required);
    const stock = stockOf(n.item_id);
    const shortage = Math.max(0, round1(required - stock));
    let bean = { bean_item_id:null, bean_code:null, bean_name:null, yield_pct:n.default_yield,
                 bean_need:null, bean_stock:null, bean_short:null };
    if (n.paired_item_id && n.default_yield > 0) {
      const bean_need  = shortage > 0 ? round1(shortage / (n.default_yield/100)) : 0;   // 부족 원두 ÷ 수율%
      const bean_stock = stockOf(n.paired_item_id);
      const bean_short = Math.max(0, round1(bean_need - bean_stock));
      const bi = meta(n.paired_item_id);
      bean = { bean_item_id:n.paired_item_id, bean_code:bi?.code ?? null, bean_name:bi?.name ?? null,
               yield_pct:n.default_yield, bean_need, bean_stock, bean_short };
    }
    return { item_id:n.item_id, item_code:n.item_code, item_name:n.item_name, unit:n.unit,
             required, stock, shortage, ...bean };
  });
  return c.json({ rows });
});
```

**응답 예시**:
```json
{ "rows": [
  { "item_id":11, "item_code":"00101", "item_name":"하우스블렌드", "unit":"kg",
    "required":30, "stock":12, "shortage":18,
    "bean_item_id":101, "bean_code":"a00101", "bean_name":"블렌드용 생두", "yield_pct":85,
    "bean_need":21.2, "bean_stock":8, "bean_short":13.2 },
  { "item_id":20, "item_code":"00202", "item_name":"싯가 원두", "unit":"kg",
    "required":5, "stock":6, "shortage":0,
    "bean_item_id":null, "bean_code":null, "bean_name":null, "yield_pct":85,
    "bean_need":null, "bean_stock":null, "bean_short":null }
]}
```
> paired 생두가 없거나 부족이 0이면 생두 칸은 `null`(화면에서 `-`). 부족 원두를 수율로 나눠 필요 생두를 구한다: `필요생두 = 부족원두 ÷ (수율%/100)`.

### 3.3 일반전표 — `/api/gl-entries` (gl.mjs) ⭐

**분개 1건 = 헤더(일자+적요) + 라인들(계정/차변/대변/거래처/적요)**. 차대변 합계 일치를 **서버가 강제**(불일치 → 400, 저장 거부). 채번은 `doc_seq`의 `seq_key='gl'`로 `YYYYMMDD-N`. `entry_type='일반'`, `doc_id/receipt_id=NULL`.

#### `GET /api/gl-entries?from=&to=` — 목록(전표 단위, 라인 포함)

```js
glEntries.post('/gl-entries', async (c) => {
  const body = await readBody(c);
  if (!body) return err(c, 400, '요청 본문이 올바르지 않습니다.');
  const ioDate = body.io_date;
  if (!isValidDate(ioDate)) return err(c, 400, '일자를 입력하세요.');
  const summary = String(body.summary ?? '');

  const lines = (Array.isArray(body.lines) ? body.lines : [])
    .map(l => ({ code:String(l.account_code ?? '').trim(),
                 dr:Math.trunc(Number(l.dr)||0), cr:Math.trunc(Number(l.cr)||0),
                 partner_id:Number(l.partner_id)||null, remarks:String(l.remarks ?? '') }))
    .filter(l => l.code && (l.dr>0 || l.cr>0));            // 계정+금액 있는 줄만
  if (lines.length < 2) return err(c, 400, '차변·대변을 합쳐 2줄 이상 입력하세요.');
  if (lines.some(l => l.dr>0 && l.cr>0)) return err(c, 400, '한 줄에 차변과 대변을 동시에 입력할 수 없습니다.');
  const sumDr = lines.reduce((s,l)=>s+l.dr,0), sumCr = lines.reduce((s,l)=>s+l.cr,0);
  if (sumDr !== sumCr) return err(c, 400, `차변합계(${sumDr.toLocaleString()})와 대변합계(${sumCr.toLocaleString()})가 일치하지 않습니다.`);

  const accs = new Map();
  for (const l of lines) if (!accs.has(l.code)) {
    const a = db.prepare(`SELECT id, code, name FROM account WHERE code=?`).get(l.code);
    if (!a) return err(c, 400, `계정과목(${l.code})을 찾을 수 없습니다.`);
    accs.set(l.code, a);
  }
  try {
    const id = db.transaction(() => {
      const docNo = nextSeqNo(ioDate, 'gl');
      const headPartner = lines.find(l => l.partner_id)?.partner_id ?? null;
      const jid = db.prepare(`
        INSERT INTO journal (doc_id, receipt_id, entry_type, io_date, doc_no, partner_id, summary)
        VALUES (NULL, NULL, '일반', ?, ?, ?, ?)`).run(ioDate, docNo, headPartner, summary).lastInsertRowid;
      const ins = db.prepare(`
        INSERT INTO journal_line (journal_id, line_no, account_id, account_code, account_name, dr, cr, partner_id, remarks)
        VALUES (?,?,?,?,?,?,?,?,?)`);
      lines.forEach((l, i) => { const a = accs.get(l.code);
        ins.run(jid, i+1, a.id, a.code, a.name, l.dr, l.cr, l.partner_id, l.remarks); });
      return jid;
    })();
    return c.json({ id, doc_no: db.prepare(`SELECT doc_no FROM journal WHERE id=?`).get(id).doc_no }, 201);
  } catch (e) { return err(c, 400, friendlySqlError(e, '전표')); }
});
```
- (선택) `PUT /api/gl-entries/:id`: 동일 검증 후 트랜잭션 안에서 `DELETE journal_line WHERE journal_id=? / UPDATE journal(io_date,summary,partner_id) / 라인 재삽입`. 전표번호(doc_no)는 불변. 없으면 클라는 "삭제 후 재입력"으로 대체 가능 → **MVP는 POST/DELETE만 필수, PUT은 선택**.

### 3.4 자금현황 — `GET /api/cash?from=&to=` (cash.mjs)

`receipt` 기반. 결제수단별 수금(입금)/지불(출금) 집계 + 일별 입출금 목록. 스펙 버킷은 **현금 / 보통예금 / 카드 / 기타**(받을어음은 '기타'로 합산).
```js
cash.get('/cash', (c) => {
  const from = isValidDate(c.req.query('from')) ? c.req.query('from') : monthStartISO();
  const to   = isValidDate(c.req.query('to'))   ? c.req.query('to')   : todayISO();
  const rows = db.prepare(`
    SELECT r.io_date, r.kind, r.method, r.amount, r.receipt_no, r.memo, p.name AS partner_name
    FROM receipt r JOIN partner p ON p.id=r.partner_id
    WHERE r.io_date>=? AND r.io_date<=? ORDER BY r.io_date, r.id`).all(from, to);
  const bucket = (m) => (m==='현금'||m==='보통예금'||m==='카드') ? m : '기타';   // 받을어음·기타 → '기타'
  const methods = ['현금','보통예금','카드','기타'];
  const byM = Object.fromEntries(methods.map(m => [m, { method:m, in_amt:0, out_amt:0 }]));
  let totalIn = 0, totalOut = 0;
  const list = rows.map(r => {
    const b = byM[bucket(r.method)];
    const isIn = r.kind === '수금';
    if (isIn) { b.in_amt += r.amount; totalIn += r.amount; } else { b.out_amt += r.amount; totalOut += r.amount; }
    return { io_date:r.io_date, kind:r.kind, partner_name:r.partner_name, method:r.method,
             receipt_no:r.receipt_no, in_amt: isIn?r.amount:0, out_amt: isIn?0:r.amount, memo:r.memo };
  });
  return c.json({
    summary: methods.map(m => ({ ...byM[m], net: byM[m].in_amt - byM[m].out_amt })),
    list,
    totals: { in_amt: totalIn, out_amt: totalOut, net: totalIn - totalOut },
  });
});
```

### 3.5 거래처 메시지 — `GET /api/message?from=&to=&partner_id=` (message.mjs)

기간 내 **판매(sale) 전표**를 거래처별로 묶어 안내문 생성 재료(라인 = 품목/수량/단가/금액, 합계)를 준다. 템플릿 자체는 `settings`(아래 4.6) 두 키로 저장/조회(기존 `/api/settings` 사용, 신규 API 아님).
```js
messageApi.get('/message', (c) => {
  const from = isValidDate(c.req.query('from')) ? c.req.query('from') : todayISO();   // 메시지는 기본 '오늘'
  const to   = isValidDate(c.req.query('to'))   ? c.req.query('to')   : from;
  const partnerId = Number(c.req.query('partner_id')) || 0;
  let dsql = `
    SELECT d.id, d.partner_id, p.name AS partner_name
    FROM doc d JOIN partner p ON p.id=d.partner_id
    WHERE d.doc_type='sale' AND d.io_date>=? AND d.io_date<=?`;
  const params = [from, to];
  if (partnerId) { dsql += ` AND d.partner_id=?`; params.push(partnerId); }
  dsql += ` ORDER BY p.name, d.io_date, d.id`;
  const lineStmt = db.prepare(`
    SELECT i.name AS item_name, i.unit, dl.qty, dl.price, (dl.supply_amt + dl.vat_amt) AS amount
    FROM doc_line dl JOIN item i ON i.id=dl.item_id WHERE dl.doc_id=? ORDER BY dl.line_no`);
  const map = new Map();
  for (const d of db.prepare(dsql).all(...params)) {
    if (!map.has(d.partner_id)) map.set(d.partner_id, { partner_id:d.partner_id, partner_name:d.partner_name, lines:[], total:0 });
    const g = map.get(d.partner_id);
    for (const l of lineStmt.all(d.id)) { g.lines.push(l); g.total += l.amount; }
  }
  return c.json([...map.values()]);
});
```

```js
beanPrice.get('/bean-price', (c) => {
  const from = c.req.query('from'), to = c.req.query('to');
  const hasFrom = isValidDate(from), hasTo = isValidDate(to);
  const per = (alias) => {
    let s = ''; const p = [];
    if (hasFrom) { s += ` AND ${alias}.io_date>=?`; p.push(from); }
    if (hasTo)   { s += ` AND ${alias}.io_date<=?`; p.push(to);   }
    return { s, p };
  };
  const items = db.prepare(`SELECT id, code, name, unit FROM item WHERE item_type='원재료' AND active=1 ORDER BY code`).all();
  const rows = [];
  for (const it of items) {
    const f = per('d');
    const a = db.prepare(`
      SELECT COUNT(*) AS cnt, COALESCE(SUM(dl.qty),0) AS qty, COALESCE(SUM(dl.supply_amt),0) AS supply,
             MAX(d.io_date) AS last_date, MIN(dl.price) AS min_price
      FROM doc_line dl JOIN doc d ON d.id=dl.doc_id
      WHERE d.doc_type='purchase' AND dl.item_id=?${f.s}`).get(it.id, ...f.p);
    if (!a.cnt) continue;
    const recent = db.prepare(`
      SELECT dl.price, d.io_date, pt.name AS partner_name
      FROM doc_line dl JOIN doc d ON d.id=dl.doc_id LEFT JOIN partner pt ON pt.id=d.partner_id
      WHERE d.doc_type='purchase' AND dl.item_id=?${f.s} ORDER BY d.io_date DESC, d.id DESC LIMIT 1`).get(it.id, ...f.p);
    const minRow = db.prepare(`
      SELECT pt.name AS partner_name FROM doc_line dl JOIN doc d ON d.id=dl.doc_id LEFT JOIN partner pt ON pt.id=d.partner_id
      WHERE d.doc_type='purchase' AND dl.item_id=?${f.s} ORDER BY dl.price ASC, d.io_date DESC LIMIT 1`).get(it.id, ...f.p);
    rows.push({
      item_id:it.id, item_code:it.code, item_name:it.name, unit:it.unit,
      recent_price: recent?.price ?? 0, recent_date: a.last_date,
      min_price: a.min_price ?? 0, min_partner: minRow?.partner_name ?? null,
      avg_price: a.qty > 0 ? Math.round(a.supply / a.qty) : 0,
      total_qty: round1(a.qty), buy_count: a.cnt,
    });
  }
  const f2 = per('d');
  const monthly = db.prepare(`
    SELECT substr(d.io_date,1,7) AS ym, COALESCE(SUM(dl.qty),0) AS qty, COALESCE(SUM(dl.supply_amt),0) AS supply
    FROM doc_line dl JOIN doc d ON d.id=dl.doc_id JOIN item i ON i.id=dl.item_id
    WHERE d.doc_type='purchase' AND i.item_type='원재료'${f2.s}
    GROUP BY ym ORDER BY ym`).all(...f2.p);
  return c.json({ rows, monthly });
});
```

### 4.1 로트조회 — `client/src/screens/LotScreen.tsx` (export `LotScreen`, id `lot`, 그룹 재고)

- **검색바**: 기간(from~to, 기본 이번달~오늘) + 산출품목 코드도움(선택, `CodeHelp endpoint="/api/items"`, ✕로 해제) + `검색(F3)`. 엑셀 버튼.
- **목록 그리드**(`/api/roast-docs`): 일자 / 전표번호 / 산출품목(`output_item_name`) / 투입내역(`input_summary`) / 투입합계(`input_total`, kg) / 산출(`output_total`, kg) / 수율(`yield_pct`%, null=`-`). 우측 정렬 수량은 `fmtQty`.
- **행 클릭 → 투입 라인 상세**: 선택 로트의 `inputs[]`를 **하단 상세 패널**(또는 Modal)에 표(품목코드/품목명/투입kg) + 산출/수율 요약으로 표시. 추가 API 호출 없음(행에 이미 포함). `onRowClick`으로 선택 상태 저장.
- 상단 요약 줄(`hint roast-yield`): 로트 수 / 총 투입 / 총 산출(그리드 합).

### 4.2 소요량계산 — `client/src/screens/MrpScreen.tsx` (export `MrpScreen`, id `mrp`, 그룹 생산)

- **검색바**: `조회(F3)` + 안내 `hint`("대기 상태 주문서 기준으로 계산합니다"). 엑셀 버튼.
- **표**(`/api/mrp` rows): **품목 / 필요(`required`) / 현재고(`stock`) / 부족(`shortage`) / 필요생두(`bean_need`) / 생두재고(`bean_stock`) / 생두부족(`bean_short`)**. 생두 관련 null은 `-`(paired 생두 없음).
  - `shortage > 0` → 빨간 강조(`danger-text`). `bean_short > 0` → 빨간 강조(**발주 참고량**).
  - 생두명 툴팁/보조열로 `bean_name` 노출(어느 생두인지). 하단 요약: 부족 품목 수 / 발주 필요 생두 종수.
- 데이터 없으면 "대기 중인 주문이 없습니다" 플레이스홀더.

### 4.3 생산입고 조회 — `client/src/screens/ProdInScreen.tsx` (export `ProdInScreen`, id `prod-in`, 그룹 생산)

이카운트 "생산입고 입력/조회" 관계: **입력=`roast-sheet`(RoastInput) / 조회=`prod-in`**. 조회 화면에서 로트를 찾아 **더블클릭 → 로스팅 전표 수정 모드로 진입**.

- **검색바**: 기간 프리셋(StatementPrint `preset()` 패턴 재사용: 금일/전일/금주/전주/금월/전월/다시작성) + `검색(F8)`. 엑셀 버튼.
- **목록 그리드**(`/api/roast-docs`): 일자 / 전표번호 / 공장(`warehouse_name`) / 산출품목 / 투입합계 / 산출 / 수율 / 적요(`memo`).
- **더블클릭 → 수정(RoastInput 재사용)**: 선택 `id`를 상태에 담고, 그리드 아래(또는 Modal)에 `<RoastInput initialEditId={id} key={id} />`를 렌더한다. RoastInput은 `initialEditId`가 오면 마운트 시 `loadForEdit(id)`로 **해당 로트를 편집 모드로 자동 로드**(일자/공장/산출/투입/적요 + 저장·삭제·수율 검증 전부 재사용). 저장/삭제 성공 시 상위 목록을 재조회.
  - **재사용을 위한 유일한 예외 변경**(6장 분담에 명시): `RoastInput`에 3줄만 추가 —
    ```tsx
    export function RoastInput({ initialEditId }: { initialEditId?: number } = {}) {
      // ...기존 훅 선언 뒤에 추가:
      useEffect(() => { if (initialEditId) loadForEdit(initialEditId); /* eslint-disable-next-line */ }, [initialEditId]);
    ```
    `initialEditId` 미전달 시 기존 동작과 100% 동일(하위호환). `loadForEdit`는 이미 존재.

### 4.4 일반전표(경비) — `client/src/screens/GlEntryScreen.tsx` (export `GlEntryScreen`, id `gl-entry`, 그룹 회계) ⭐

가장 중요. **입력부(수동 분개) + 조회부(기간 목록·삭제)** 한 화면.

- **입력 헤더**: 일자(date, 기본 오늘) + 적요(text, `grow`). RoastInput의 `voucher-head` 레이아웃 재사용.
- **라인 그리드**(`voucher-lines` 테이블 스타일 재사용): 각 행 = No / 계정(코드도움 `endpoint="/api/accounts"`, readonly lookup) / 차변(number) / 대변(number) / 거래처(선택, 코드도움 `/api/partners`, ✕ 해제) / 적요(text) / 삭제(✕). `+ 라인 추가` 버튼(기본 2줄 제공). 한 줄에 차·대 동시 입력 시 다른 쪽을 0으로 강제(온체인지에서).
- **실시간 차대변 합계 바**: 그리드 하단 고정 —
  `차변합계 {fmtWon(sumDr)}  /  대변합계 {fmtWon(sumCr)}  /  차액 {fmtWon(sumDr-sumCr)}`.
  차액≠0 이면 빨강(`danger-text`) + **[저장] 버튼 disabled**. 차액=0 이고 라인≥2 이면 초록/활성.
- **저장**: `POST /api/gl-entries`. 성공 → toast(`전표 {doc_no} 저장`), 입력부 초기화(일자 유지), 목록 재조회. **서버도 균형을 재검증**(클라 우회 방지)하므로 400 메시지를 그대로 toast.
- **조회부(하단)**: 기간(from~to, 기본 이번달~오늘) + `검색(F3)`. `GET /api/gl-entries` → 전표 목록 그리드: 일자 / 전표번호 / 적요 / 금액(`amount`=차변합계) / 삭제(✕ → `Confirm` → `DELETE`). 행 클릭 시 라인 펼침(하위 표: 계정/차변/대변/거래처/적요) — `lines[]` 이미 포함.
- 힌트: "경비·대체 분개를 직접 입력합니다. 저장 시 분개장·월별손익(판매관리비)·거래처원장에 자동 반영됩니다."

### 4.6 거래처 메시지 — `client/src/screens/MessageScreen.tsx` (export `MessageScreen`, id `message`, 그룹 영업)

기존 앱 이식: 거래처(또는 전체) + 기간(기본 오늘) → 판매내역으로 안내문 생성. 카드 나열 UX.

    - 주문확인: `안녕하세요 {거래처명}님, 주문 확인드립니다.\n{내역}\n합계 {합계}원({합계한글}원정) 입니다. 감사합니다.`

- **결과 카드 목록**(거래처별 `msg-card`): 거래처명 + 활성 템플릿으로 치환한 본문을 `textarea`(수정 가능)로 표시 + `[복사]` 버튼(`navigator.clipboard.writeText`, 성공 toast). 상단에 템플릿 종류 라디오(주문확인/택배안내)로 전체 카드 본문 일괄 전환. 내역이 없으면 "기간 내 판매 내역이 없습니다".
- `{내역}` 치환은 서버 `lines`로 클라가 조립(3.5 참조). `{합계한글}`은 `wonToKorean`(format.ts).

## 9. 자가검증 시나리오 (DoD)

1. **마이그레이션 006**: 기동 시 `[DB] 마이그레이션 적용: 006_gl_entry.sql` 1회. 재기동 시 미적용(멱등). 기존 자동분개 보존.
2. **gl-entry 균형**: 819 차변 500,000 / 103 대변 500,000 저장 성공 → 전표번호 발급. 차액 있는 상태로 저장 시도 → 버튼 비활성 + (강제 우회해도) 서버 400 "차변합계…대변합계…일치하지 않습니다".
3. **자동 합류**: 위 전표가 **분개장('전체')**·**월별손익 판매관리비**(해당 월 +500,000)에 나타남. 삭제 시 두 곳에서 사라짐. 판매 전표 삭제해도 일반전표는 생존.
4. **lot/prod-in**: 로스팅 전표 저장 후 lot에 로트 1행, 행 클릭 시 투입 라인 상세. prod-in 더블클릭 → RoastInput 편집 모드로 그 로트 로드 → 수정 저장 반영.
