## 1. API 계약 8개 (복붙 수준)

### 공통 규약
- 모든 API는 **GET**, 응답은 JSON. 금액은 정수(원), 수량은 kg 소수 1자리.
- 기간 파라미터 `from`/`to`는 `YYYY-MM-DD`. 미지정/형식오류 시 `from`=이번달 1일, `to`=오늘(기존 `isValidDate` 규칙, accounting.mjs와 동일).
- **응답 봉투(envelope) 2형태**:
  - **집계/목록형**(총계정원장·시산표·수금·지급·이익현황): `{ rows: [...], summary: {...} }`
  - **원장형**(계정별원장·현금출납장): `{ meta: {...}, opening, rows: [...], sum_dr, sum_cr, closing }` — 거래처원장(`/api/partner-ledger`)과 동형.
- 에러: `err(c, 400, '메시지')` → `{ error: '메시지' }`. 원장형에서 필수 계정 미선택 시 400.

### 1.1 계정별원장 — `GET /api/account-ledger`
계정 1개를 선택해 기간 내 분개 라인 + 이월/러닝 잔액을 본다. 거래처원장의 계정 버전.

**요청**: `?account_code=108&from=2026-07-01&to=2026-07-31`
- `account_code` **필수**(없으면 400 `'계정과목을 선택하세요.'`)
- `partner_id` 선택(해당 계정 라인 중 특정 거래처만)

**응답**:
```json
{
  "meta": { "account": { "code": "108", "name": "외상매출금", "category": "자산", "dr_side": true } },
  "opening": 600000,
  "rows": [
    { "io_date": "2026-07-03", "doc_no": "20260703-1", "entry_type": "매출", "partner_name": "(주)이카운트", "dr": 2200000, "cr": 0, "balance": 2800000, "summary": "" },
    { "io_date": "2026-07-05", "doc_no": "20260705-1", "entry_type": "매출", "partner_name": "(주)이한에프엔비", "dr": 550000, "cr": 0, "balance": 3350000, "summary": "" },
    { "io_date": "2026-07-10", "doc_no": "20260710-1", "entry_type": "수금", "partner_name": "(주)이카운트", "dr": 0, "cr": 1000000, "balance": 2350000, "summary": "" },
    { "io_date": "2026-07-11", "doc_no": "20260711-1", "entry_type": "수금", "partner_name": "(주)이한에프엔비", "dr": 0, "cr": 300000, "balance": 2050000, "summary": "" }
  ],
  "sum_dr": 2750000, "sum_cr": 1300000, "closing": 2050000
}
```
- `dr_side`: 차변성 계정(자산·비용)=`true`, 대변성(부채·자본·수익)=`false`. **잔액 방향 결정에 사용**(§2.1).
- `balance`: 이월에서 시작해 라인마다 누적한 러닝 잔액.

### 1.2 총계정원장 — `GET /api/general-ledger`
전 계정(활동 있는 계정만)의 기간 요약 원장: 전기이월 + 차변합계 + 대변합계 + 잔액.

**요청**: `?from=2026-07-01&to=2026-07-31`
- `category` 선택(자산/부채/자본/수익/비용 필터)

**응답**:
```json
{
  "rows": [
    { "code": "101", "name": "현금",       "category": "자산", "opening": 0,       "dr": 1000000, "cr": 80000,   "balance": 920000 },
    { "code": "103", "name": "보통예금",   "category": "자산", "opening": 500000,  "dr": 300000,  "cr": 600000,  "balance": 200000 },
    { "code": "108", "name": "외상매출금", "category": "자산", "opening": 600000,  "dr": 2750000, "cr": 1300000, "balance": 2050000 },
    { "code": "251", "name": "외상매입금", "category": "부채", "opening": 440000,  "dr": 600000,  "cr": 880000,  "balance": 720000 },
    { "code": "404", "name": "제품매출",   "category": "수익", "opening": 1000000, "dr": 0,       "cr": 2500000, "balance": 3500000 }
  ],
  "summary": { "sum_dr": 4650000, "sum_cr": 5360000 }
}
```
- `opening`: `from` 직전까지의 잔액(방향 반영). `balance`: `opening` + 기간 순증(방향 반영).
- `dr`/`cr`: 기간 내 차변·대변 **합계**(방향 미반영, 원시 합).
- `summary.sum_dr`/`sum_cr`: 기간 차·대 총합(항상 일치 → 검증 지표).

## 2. 서버 계산 규칙

`finreports.mjs`는 `db.mjs`의 `db`, `ledger.mjs`의 `err`/`isValidDate`/`todayISO`를 import. accounting.mjs와 동일한 `monthStartISO()` 로컬 헬퍼 사용.

### 2.1 이월(opening) 잔액 계산 경계 — 원장형 공통
거래처원장(accounting.mjs:285-290)과 **동일한 경계**를 쓴다.
- **이월 = `io_date < from`** 인 라인들의 잔액(방향 반영). 경계는 `<`(from 당일은 이월에 포함하지 않음 — 당일 라인은 rows에 표시).
- **방향(dr_side)**: 계정 `category`가 `자산`·`비용`이면 차변성(`dr_side=true`), `부채`·`자본`·`수익`이면 대변성(`dr_side=false`).
- 산식:
  ```sql
  -- openRaw = Σ(dr-cr)  WHERE account_code=? AND io_date < from
  ```
  ```js
  const opening = dr_side ? openRaw : -openRaw;      // 대변성은 부호 반전
  // 러닝: balance += dr_side ? (dr - cr) : (cr - dr)
  ```
- `from` 미지정(형식오류) 시 기본값(이번달 1일)이 적용되므로 이월은 그 이전 누계. 전체 이력을 보려면 `from`을 아주 과거로.

> **검증(§2.6)**: 108(자산) 이월 600,000 / 잔액 2,050,000, 251(부채) 이월 440,000 / 잔액 720,000, 404(수익) 이월 1,000,000 / 잔액 3,500,000 — 전부 수기 대조 PASS.

### 2.2 총계정원장
- 대상: 기간 내 활동(라인)이 있거나 이월이 0이 아닌 계정. 구현은 "기간 내 라인이 있는 account_code" ∪ "io_date<from 라인이 있는 account_code"를 계정 순으로.
- 각 계정: `opening`(§2.1 방향 반영), `dr`=Σdr(기간), `cr`=Σcr(기간), `balance`=opening + (dr_side ? dr-cr : cr-dr).
- `summary.sum_dr`=Σ 전 계정 dr, `sum_cr`=Σ 전 계정 cr → **항상 일치**(균형 지표).

### 2.3 현금출납장
- 계정별원장의 특화. `account_code`를 101/103으로 제한, 컬럼을 입금(dr)/출금(cr)으로 리네이밍.
- `kind` 라벨 매핑: journal.entry_type `수금`→`수금`, `지불`→`지불`, `일반`이면서 해당 라인 dr>0→`수입`, cr>0→`지출`, `매출`/`매입`→그대로(현금거래가 자동분개로 잡히는 경우 대비).
- opening/러닝은 §2.1과 동일(현금·예금은 자산=차변성이므로 입금(+)/출금(−)이 잔액에 그대로 반영).
- **구현 팁**: 계정별원장과 공통 하부 함수 `ledgerRows(accountCode, from, to, partnerId?)`로 뽑고, 현금출납장은 라벨만 바꿔 반환(중복 SQL 회피).

### 2.4 손익계산서 단계 산식 — 월별손익과 일치 보장
**핵심**: `/api/income-statement`의 매출·원가·판관비 소스 표현식을 `/api/monthly-pl`(accounting.mjs:327-354)과 **문자 그대로 동일**하게 둔다. 차이는 기간 필터(`io_date BETWEEN from AND to`) vs 연/월 필터(`substr`)뿐.

| 단계 | 산식(월별손익과 동일 소스) |
|---|---|
| 매출액 | `SUM(doc.total_supply) WHERE doc_type='sale' AND io_date∈[from,to]` |
| 매출원가 | `SUM(doc.total_supply) WHERE doc_type='purchase' AND io_date∈[from,to]` |
| 매출총이익 | 매출액 − 매출원가 |
| 판매비와관리비 | `SUM(jl.dr - jl.cr)` JOIN account `WHERE a.category='비용' AND jl.account_code LIKE '8%' AND j.io_date∈[from,to]` |
| 영업이익 | 매출총이익 − 판매관리비 |

- 판관비 **명세(details)**: 위 필터를 `GROUP BY jl.account_code`로 쪼갠 것. 합은 판관비 총액과 일치.
- 매출·원가 명세: 단일 요약행(제품·상품 매출 / 상품·원재료 매입액). 원장의 진실(doc)을 따르며 journal 수익계정과도 일치(자동분개가 제품매출=total_supply로 대변 기록하므로 등가).
- **일치 보장 테스트(문서화된 계약)**: `income-statement(YYYY-01-01 ~ YYYY-12-31)`의 각 단계 `amount` == `monthly-pl(YYYY)` `rows[].total`. §2.6에서 7월 구간이 monthly-pl 7월 컬럼과 일치함을 확인(매출 2,500,000 / 원가 800,000 / 판관비 80,000).

> ⚠️ 소넷 구현 시 주의: 월별손익 판관비 주석대로 자동분개는 판관비를 만들지 않는다. 판관비는 **일반전표(gl-entry, entry_type='일반')**로만 발생한다. 손익계산서도 동일 경로로 잡히므로 두 보고서가 자동 일치한다. 새 SQL을 짜지 말고 monthly-pl의 3개 쿼리 표현식을 그대로 복사할 것.

### 2.5 이익현황 원가단가 소스 (우선순위)
품목별 원가단가 `cost_unit(item)`:
1. `item.price_in > 0` → `price_in` 사용, `cost_source='std'`
2. 아니면 그 품목의 **실매입 가중평균** = `SUM(dl.supply_amt) / SUM(dl.qty)` (구매 doc_line, `io_date <= to` 전체, qty>0) → `cost_source='avg'`
3. 둘 다 없으면 `0`, `cost_source='none'`

- `cost = round(qty * cost_unit)`, `margin = sales − cost`, `margin_pct = sales>0 ? round(margin/sales*100) : 0`.
- **로스팅 구조 한계 명시**: 판매품(제품/원두)은 직접 매입이 없고 로스팅(생두→원두)으로 생산되므로, BOM 기반 실원가는 R1 범위 밖. R1은 표준단가(price_in) 우선·실매입 폴백의 **근사 원가**를 쓰고 `cost_source`로 신뢰도를 표기한다. BOM 원가 연동은 향후(R2/R3) 확장 포인트로 코드에 `// TODO: BOM 원가` 주석.
- group=partner일 때: `dl.item_id` 대신 `d.partner_id`로 GROUP BY, 원가는 라인별 cost_unit 합산.

## 3. ReportScreen 컴포넌트 스펙 + 보고서 정의 8개

### 3.1 정의 객체 타입 (`reportDefs.ts` / `types.ts`)
```ts
type FilterKind = 'date-range' | 'account' | 'partner' | 'select' | 'as-of';

interface ReportFilter {
  key: string;                 // 쿼리 파라미터 이름 (date-range는 from/to 고정)
  kind: FilterKind;
  label?: string;
  required?: boolean;          // true면 값 없을 때 자동조회 안 함(계정별원장 account)
  default?: string;            // select/as-of 초기값
  options?: string[];          // select 옵션
  omitWhen?: string;           // 이 값이면 파라미터 미전송 (예: '전체')
  helpEndpoint?: string;       // account: '/api/accounts', partner: '/api/partners'
  width?: number;
}

interface ReportColumn {       // Tabulator ColumnDefinition의 얇은 래퍼
  title: string; field: string; width?: number; minWidth?: number;
  align?: 'left' | 'center' | 'right';
  fmt?: 'won' | 'qty' | 'pct' | 'text';   // 포매터 프리셋
  sum?: boolean;               // 하단 bottomCalc 합계
  bold?: boolean;              // 값 굵게(잔액 컬럼 등)
}

interface ReportDef {
  id: string;
  title: string;
  endpoint: string;            // '/api/account-ledger'
  filters: ReportFilter[];
  columns: ReportColumn[];
  rowsPath?: 'rows';           // 응답이 배열이 아니면 이 경로에서 rows 추출. 기본 'rows'
  summaryLine?: (env: any) => string;   // ledger-summary 힌트 문자열(옵션)
  fileName?: string;           // 엑셀 파일명. 기본 `${title}.xlsx`
  autoSearch?: boolean;        // 마운트 시 자동 조회(기본 true, required 필터 있으면 값 충족 시에만)
}
```
- `footerSums`는 `columns[].sum:true`로 표현(별도 필드 불필요).
- `transform`이 필요한 보고서는 R1엔 없음(전부 서버가 표시형으로 내려줌). 타입엔 `transform?: (env)=>Row[]` 예약만 두고 미사용.

### 3.2 ReportScreen props & 동작
```ts
interface ReportScreenProps { def: ReportDef; }
export function ReportScreen({ def }: ReportScreenProps) { … }
```
동작:
1. **필터 상태**: date-range는 `from`/`to`(기본 `monthStartISO()`~`todayISO()`), as-of는 `as_of`(기본 today), select는 `default`, account/partner는 `{code/id, name}`.
2. **조회(load)**: 필터로 querystring 구성. `omitWhen`·빈 값·`required` 미충족은 미전송. `required` 필터가 비면 조회 보류(토스트 안내). 응답을 `rows`(배열이면 그대로, 아니면 `env.rows`)로 그리드에 세팅, `summaryLine(env)`로 힌트 렌더.
3. **자동조회**: 마운트/필터 변경 시(`useCallback`+`useEffect`), required 충족 시에만(거래처원장 패턴).
4. **컬럼 빌드**: `fmt`→포매터(won=`fmtWon`, qty=`fmtQty`, pct=`n%`), `align`, `sum`→`bottomCalc:'sum'`+`bottomCalcFormatter`(won). `bold`→`<b>` 래핑. 정의가 바뀔 일이 없으므로 `<DataGrid key={def.id}>`.

### 3.3 검색조건 저장 탭 (C그룹 — ReportScreen 내장, 8종 자동 적용)
- **UI**: 조회 바 위 탭 스트립. `[기본] [탭2] … [+]`. 활성 탭 강조. 비-기본 탭에 hover 시 `✕`(삭제).
- **저장 위치**: `localStorage['reportTabs:'+def.id]` = `Array<{ name: string; cond: Record<string,string> }>`. `cond`는 필터 key→값 스냅샷(account/partner는 `code`/`id`+`name` 함께).
- **동작**:
  - `기본` 탭(index 0)은 항상 존재·삭제 불가. 초기 상태는 def 기본값.
  - `[+]`: 현재 필터값을 스냅샷으로 캡처 → 탭 이름 `prompt('검색조건 이름')` → 배열에 push + localStorage 저장 + 그 탭 활성화.
  - 탭 클릭: 저장된 `cond`를 필터 상태에 주입 후 즉시 조회.
  - `✕`: 해당 탭 삭제(localStorage 갱신), 기본 탭으로 이동.
  - 필터를 바꾸고 다시 조회하면 **활성 탭의 cond를 그 값으로 갱신**(기본 탭 제외 — 기본 탭은 def 기본값 유지). 
- **격리**: `def.id`별 독립 저장 → 보고서마다 자기 탭.

### 3.4 단축키·버튼 관례 (이카운트 정합)
- **조회**: 조회 바에 `[검색(F3)]` 버튼. **F3**과 **F8** 둘 다 조회에 바인딩(입력 폼이 없는 조회 화면이므로 충돌 없음 — StatementPrint는 F8, 분개장류는 F3을 써왔기에 둘 다 지원해 근육기억 흡수). `keydown` 리스너에서 `e.key==='F3'||e.key==='F8'` → `preventDefault()` + load.

## 6. 결정 근거 · 주의

1. **파일 겹침 0**: 신규 회계 보고서는 accounting.mjs(420줄)에 넣지 않고 `finreports.mjs`로 분리(플랜 구조 결정). index.mjs는 1줄.
2. **손익-월별손익 일치**: 새 SQL을 만들지 않고 monthly-pl 쿼리 표현식을 복사 → 두 보고서가 구조적으로 동일 소스(doc sale/purchase total_supply + 8x 일반전표 판관비). 검증 PASS.
3. **원장 방향 일반화**: 거래처원장은 매출/매입 side로 방향을 골랐지만, 계정별원장은 계정 category(자산·비용=차변성)로 일반화. 자산·부채·수익 계정 모두 수기 대조 PASS.
4. **이익현황 원가 한계**: 로스팅(생두→원두) 때문에 판매품에 직접 매입원가가 없음 → price_in→실매입평균→0 폴백 + `cost_source` 표기. 현재 실데이터(price_in=0)에선 원가 0으로 정직하게 표시. BOM 원가는 후속.
5. **검색조건 저장 탭은 ReportScreen 1곳**: C그룹 요구를 엔진에 내장 → 그리드형 7종(+R2 추가분) 자동 상속. 손익계산서(서식형)는 탭 미적용(단일 기간 서식).
