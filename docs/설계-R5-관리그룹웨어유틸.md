# 설계 — R5 관리 + 그룹웨어 + 유틸(최종 라운드) (100% 완성 플랜)

> 승인 플랜(`/root/.claude/plans/100-dazzling-pnueli.md`) **R5 라운드 + D그룹 잔여** 상세 설계. 문서 형식은 `docs/설계-R4-세무회계2.md`를 따른다.
> **범위 9가지** — 관리: ① 급여대장(간이) ② 근태관리(간이). 그룹웨어: ③ 게시판(메모 통합) ④ To Do(MyPage 위젯 연동). Self-Customizing: ⑤ 엑셀 업로드/다운로드 ⑥ 백업/복원 ⑦ 기존앱 데이터 이관. 연동 stub: ⑧ 계좌/카드 연동 ⑨ 외화·WMS·POS·쇼핑몰(공용 StubScreen).
> **사용자 확정 방침**: "화면·데이터·계산은 로컬로 동작, 외부 연동 버튼은 '연동 예정' 비활성 stub." → 급여 4대보험·소득세는 **로컬 간이 계산(참고용)**, 요율은 `settings`에 두어 화면에서 수정 가능. 급여이체·연말정산·국세청/은행 연동은 stub.
> **불변식**: 기존 **69개 메뉴 id 전부 동결**(R4 종료 시점 69개 — §1.4 집계로 확정). placeholder 4개(`memo`·`io`·`backup`·`migrate`)는 **id 유지·컴포넌트만 실화면 교체**(메뉴명 변경 가능). 신규 메뉴만 새 id. 마이그레이션 번호 **009**(008까지 적용됨 — **009 = 마지막 선점 번호**).
> **파일 겹침 0**: 서버 소넷 = **신규 `server/hr.mjs`·`server/groupware.mjs`·`server/admin.mjs` + `server/migrations/009_hr_groupware.sql` + `server/index.mjs`(import 3줄·route 3줄) + `server/mypage.mjs`(todos 채우기 1블록)만**. 클라 소넷 = **신규 화면 8파일 + `menus.tsx` + `types.ts` + `styles.css`(append) + `Dashboard.tsx`(To Do 위젯 렌더)만**. `masters.mjs`·`db.mjs`·`ledger.mjs`·`App.tsx`·기존 스크립트는 **무수정**(§0 교집합표·§6).

### 1.3 관리 그룹 dim 자동 해제 (App.tsx 무수정)

R4 종료 시점 `MENU_GROUPS`는 9개(`MyPage/재고Ⅰ/재고Ⅱ/회계Ⅰ/회계Ⅱ/관리/세무/그룹웨어/Self-Customizing`)이고, 관리 그룹만 소속 메뉴 0개라 대메뉴 바에서 `reserved`(dim·클릭 no-op, App.tsx:117-119)였다. R5가 `payroll`·`attendance`를 관리에 넣으면 `MENUS.find(x=>x.group==='관리')`가 값을 반환 → **App.tsx 무수정으로 자동 활성**. 사이트맵 오버레이의 `!items.length && '예정'` 표기(App.tsx:192)도 자동으로 사라진다.

> R5 종료 후 **9개 대메뉴 전부 소속 메뉴 ≥1** → `reserved` 상태 0개 = 이카운트식 메뉴 지도 100% 완성.

### 2.1 급여 요율 = settings 재사용 (신규 테이블 없음)

`settings`(key TEXT PK, value TEXT — `001_init.sql:68`)에 `payroll_rate_*` 키로 관리. **009에서 seed하지 않는다**(migration은 CREATE만 유지). hr.mjs가 조회 시 없으면 아래 기본값으로 폴백하고, 사용자가 화면에서 저장하면 `PUT /api/settings`(또는 hr.mjs 자체 upsert)로 기록된다.

| settings key | 의미 | 기본값(참고용) |
|---|---|---|
| `payroll_rate_pension` | 국민연금(보수월액 %) | `4.5` |
| `payroll_rate_health` | 건강보험(보수월액 %) | `3.545` |
| `payroll_rate_longterm` | 장기요양(건강보험료의 %) | `12.95` |
| `payroll_rate_employment` | 고용보험(보수월액 %) | `0.9` |
| `payroll_rate_income_tax` | 소득세 간이 근사(과세급여 %) | `3.0` |

- 지방소득세는 **소득세의 10% 고정**(법정 규칙)이라 별도 요율 키를 두지 않는다(§3.2).
- 기존 `settings` 관례(company_*·vat_round)와 동일 — 키 추가만, 스키마 무변경.

**DDL 사전검증 절차**(서버 소넷 필수): `data/erp.sqlite` 사본에 `foreign_keys=ON`으로 009 적용 → 4테이블 생성·`PRAGMA foreign_key_check` 0건 → `payroll(emp_id=<존재 사원>)` upsert OK, `emp_id=9999`(미존재) FK 거부 확인 → `UNIQUE(emp_id,pay_ym)` 중복 삽입이 upsert로 흡수되는지 확인 → 사본 폐기(§5.1).

### 3.1 급여대장 목록 — `GET /api/payroll` (hr.mjs)

**요청**: `?ym=YYYY-MM`(기본 이번달). 대상 사원 전체를 LEFT JOIN → 급여 미작성 사원도 행으로 표시(작성 유도).

```sql
SELECT e.id AS emp_id, e.code AS emp_code, e.name AS emp_name,
       p.id AS payroll_id, p.pay_ym, p.pay_date,
       p.base_pay, p.allowance, p.meal_allowance,
       p.national_pension, p.health_ins, p.longterm_care, p.employment_ins,
       p.income_tax, p.local_income_tax, p.other_deduction,
       p.gross_pay, p.deduction_total, p.net_pay, p.memo
FROM employee e
LEFT JOIN payroll p ON p.emp_id = e.id AND p.pay_ym = ?
WHERE e.active = 1
ORDER BY e.code;
```

**응답**:

### 3.2 급여 간이 계산 — `GET /api/payroll/rates`·`PUT /api/payroll/rates` + 계산식 (hr.mjs)

> **⚠ 간이 계산·참고용**: 아래 요율·소득세 근사는 **정확한 원천징수가 아니다**. 실제 4대보험 상하한·간이세액표·비과세 한도·두루누리 감면 등은 반영하지 않는다. 요율은 `settings`에 두어 화면에서 수정 가능하며, 각 공제액은 급여대장에서 **수기 조정**할 수 있다. 화면·명세서·PDF에 "간이 계산(참고용)" 문구를 명시한다(§4.1).

**`GET /api/payroll/rates`** → 현재 요율(settings 폴백):
```js
const RATE_DEFAULTS = { pension:4.5, health:3.545, longterm:12.95, employment:0.9, income_tax:3.0 };
// SELECT key,value FROM settings WHERE key LIKE 'payroll_rate_%'; 없으면 RATE_DEFAULTS.
```
응답: `{ "pension":4.5, "health":3.545, "longterm":12.95, "employment":0.9, "income_tax":3.0 }`.

**`PUT /api/payroll/rates`** body `{ pension, health, longterm, employment, income_tax }` → `settings`에 `payroll_rate_*`로 upsert(masters.mjs `/settings` PUT과 동일 패턴을 hr.mjs 내부에 격리 복제 — masters.mjs 무수정). 숫자 검증(0 이상 REAL).

**간이 공제 계산식**(순수 함수 `calcDeductions(base, allowance, rates)`):
```js
// 과세보수월액 = base_pay + allowance (비과세 식대 meal_allowance는 4대보험·소득세 기준에서 제외 — 간이)
const taxable = base_pay + allowance;
const national_pension = Math.round(taxable * rates.pension   / 100);   // 국민연금 4.5%
const health_ins       = Math.round(taxable * rates.health    / 100);   // 건강보험 3.545%
const longterm_care    = Math.round(health_ins * rates.longterm / 100); // 장기요양 = 건보료 × 12.95%
const employment_ins   = Math.round(taxable * rates.employment / 100);  // 고용보험 0.9%
const income_tax       = Math.round(taxable * rates.income_tax / 100);  // 소득세 간이 근사(요율%)
const local_income_tax = Math.round(income_tax * 0.1);                  // 지방소득세 = 소득세 × 10%(고정)
```
- **소득세 근사 주석**(hr.mjs): `// TODO(간이세액표): 정확한 근로소득 간이세액표(부양가족·자녀 수 반영) 연동은 R6+. 현재는 과세급여 × 설정요율(%) 근사 — 참고용.`

### 3.3 급여 저장 — `POST /api/payroll`·`DELETE /api/payroll/:id` (hr.mjs)

**`POST /api/payroll`**(upsert on `(emp_id,pay_ym)`) body:
```jsonc
{ "emp_id":1, "pay_ym":"2026-07", "pay_date":"2026-07-25",
  "base_pay":2500000, "allowance":200000, "meal_allowance":100000, "memo":"",
  "auto":true,                       // true면 공제액을 요율로 자동계산, false면 아래 수기값 사용
  "national_pension":121500, "health_ins":95715, "longterm_care":12395,
  "employment_ins":24300, "income_tax":81000, "local_income_tax":8100, "other_deduction":0 }
```
- 검증: `emp_id` 존재(active 무관), `pay_ym` `/^\d{4}-\d{2}$/`, `pay_date` 빈값 또는 isValidDate, 금액 정수 ≥0.
- `auto:true` → `calcDeductions()`로 6개 공제액 산출(§3.2). `auto:false` → body의 공제 금액 사용(수기 조정).
- **서버가 항상 캐시 재계산**(클라 값 폐기 — doc 패턴):
  `gross_pay = base_pay+allowance+meal_allowance`, `deduction_total = Σ(6개 공제 + other_deduction)`, `net_pay = gross_pay - deduction_total`.
```sql
INSERT INTO payroll (emp_id, pay_ym, pay_date, base_pay, allowance, meal_allowance,
  national_pension, health_ins, longterm_care, employment_ins, income_tax, local_income_tax, other_deduction,
  gross_pay, deduction_total, net_pay, memo)
VALUES (?,?,?,?,?,?, ?,?,?,?,?,?,?, ?,?,?, ?)
ON CONFLICT(emp_id, pay_ym) DO UPDATE SET
  pay_date=excluded.pay_date, base_pay=excluded.base_pay, allowance=excluded.allowance,
  meal_allowance=excluded.meal_allowance, national_pension=excluded.national_pension,
  health_ins=excluded.health_ins, longterm_care=excluded.longterm_care, employment_ins=excluded.employment_ins,
  income_tax=excluded.income_tax, local_income_tax=excluded.local_income_tax, other_deduction=excluded.other_deduction,
  gross_pay=excluded.gross_pay, deduction_total=excluded.deduction_total, net_pay=excluded.net_pay, memo=excluded.memo;
```
반환: 저장된 급여 행(목록 1행 형상 + emp_code/emp_name 조인).

**`DELETE /api/payroll/:id`** → 해당 급여행 삭제(`validId`, 없으면 404).

**엣지케이스**: ① 같은 (사원,월) 재저장 → upsert(중복 없음). ② `base_pay=0` 저장 허용(공제 0). ③ `other_deduction`이 커서 `net_pay` 음수 → 허용(가불 초과 등, 경고 아님). ④ 요율 변경 후 기존 행은 자동 재계산 안 됨 — 다시 저장(`auto:true`)해야 반영(문서 명시).

### 3.5 근태관리 — `GET/POST/PUT/DELETE /api/attendance` + 월집계 (hr.mjs)

```sql
GROUP BY a.emp_id ORDER BY e.code;
```

### 3.12 지금 백업 — `POST /api/backup/now` (admin.mjs · WAL-aware 격리 복제)

`db.mjs:20-37`의 기동 백업 로직을 admin.mjs 내부 `doBackup()`으로 **격리 복제**(db.mjs 무수정):
```js
function doBackup() {
  db.pragma('wal_checkpoint(TRUNCATE)');            // -wal 커밋분을 본 파일에 합치고
  const stamp = /* YYYYMMDD-HHMMSS (db.mjs와 동일 포맷) */;
  const dest = path.join(backupDir, `erp-${stamp}.sqlite`);
  fs.copyFileSync(dbPath, dest);                    // 본 파일 복사
  // 30개 초과분 정리(db.mjs와 동일)
  return { name: path.basename(dest), size: fs.statSync(dest).size };
}
```
- `dbPath`/`backupDir`는 admin.mjs 상단에서 `db.mjs`와 동일하게 계산(`path.join(root,'data','erp.sqlite')` 등). `db`는 `import { db }`.

### 3.13 복원 — `POST /api/backup/restore` (admin.mjs) + **better-sqlite3 파일 교체 제약**

**핵심 제약(실제 코드 기준)**: `db.mjs:13`의 `export const db = new Database(dbPath)`는 **모듈 싱글턴**으로 모든 라우트가 공유하며, WAL 모드로 파일을 **연 상태로 유지**한다. 열려 있는 DB 파일을 디스크에서 덮어쓰면 손상 위험이 있어, **런타임 인-플레이스 스왑은 안전하지 않다**. `start.mjs`는 워처/자동재기동이 없다(단발 `import`).
→ **결론: 복원은 "복원 전 자동백업 → 파일 교체 → 프로세스 종료(재시작 필요)"로 설계한다.** 이는 단일 사용자 로컬 앱에서 안전한 정공법이다.

**`POST /api/backup/restore`** body `{ file, confirm:true }`(2단계 확인 — 클라가 confirm 토큰 요구, §4.5):
1. **검증**: `file`이 `data/backup/` 내부 실제 `.sqlite`인지(경로 탈출 차단 — `path.basename(file)`만 사용, `..` 거부). 없으면 404.
2. **복원 전 자동백업**: `doBackup()` 1회(현재 상태 안전망 — 잘못 복원 시 되돌리기용).
3. **응답 먼저 전송**: `{ ok:true, needs_restart:true, pre_backup:"erp-….sqlite", message:"복원이 준비되었습니다. 서버가 종료되면 다시 실행하세요." }` (브라우저가 안내를 받도록 먼저 flush).
4. **안전 스왑 후 종료**(응답 후 `setTimeout(…, 200)`):
   ```js
   db.pragma('wal_checkpoint(TRUNCATE)');
   db.close();                                   // 싱글턴 닫아 추가 쓰기 차단(이후 요청은 종료로 무의미)
   fs.copyFileSync(path.join(backupDir, file), dbPath);
   for (const sfx of ['-wal','-shm']) { const p = dbPath+sfx; if (fs.existsSync(p)) fs.unlinkSync(p); }  // stale 사이드카 제거
   process.exit(0);                              // 재시작 시 db.mjs가 복원된 파일을 깨끗이 연다(+기동 자동백업 1개 더 생성)
   ```
- **재시작 필요를 화면에 명시**: 복원 성공 후 "서버가 종료되었습니다. `npm start`로 다시 실행(또는 실행 창을 다시 열기)하세요." 안내(§4.5). 재기동 시 db.mjs 기동 백업(`db.mjs:20-37`)이 복원본을 한 번 더 백업하므로 이중 안전.
- **엣지**: 존재하지 않는 파일 → 404(종료 안 함). `confirm≠true` → 400('복원은 2단계 확인이 필요합니다'). 스왑 실패 시 pre_backup이 남아 원복 가능.
- **주석**: `// 복원은 better-sqlite3 단일 오픈 핸들 제약상 프로세스 재시작이 필요하다(런타임 인-플레이스 스왑 불가). db.mjs 무수정 유지를 위해 백업 로직은 doBackup()으로 격리 복제.`

## 5. 소넷 자가 검증 시나리오 (deliverable ⑤)

### 5.1 테스트 데이터·DB 사본 규칙 (doc_seq 원복 포함)

- **원칙**: 읽기 검증(급여 GET·근태 GET·게시판/투두 GET·백업 목록·export·migrate preview)은 실 DB에 읽기전용으로.
- **쓰기 검증은 사본 DB**: `cp data/erp.sqlite /tmp/erp-r5-test.sqlite` → 사본 열어 009 적용·CRUD·upsert·**migrate apply·io apply·backup restore** 검증 → 사본 폐기(원본 무변경). R3/R4 검증과 동일 절차.
- **migrate apply는 반드시 사본에서**: 실 DB는 전표 0건·마스터(품목 57·거래처 21·계정 27)만 유지가 검증 관례. apply는 `doc_seq`를 올리므로(§3.10) 실 DB에서 하지 않는다. 부득이 실 DB에 넣었다면 테스트 전표 k건 삭제 후 `UPDATE doc_seq SET last_no = last_no - <k> WHERE io_date='<YYYYMMDD>' AND seq_key='sale';`로 원복(그 (일자,유형)에 실 전표 없을 때만). **권장은 사본 사용 → 원복 불필요.**
- **backup restore 검증은 사본에서만**: restore는 `process.exit(0)`을 부른다(§3.13). 실 서버에서 호출하면 서버가 종료된다 → 사본 DB를 가리키는 별도 프로세스나, restore의 스왑 로직만 단위로 떼어 검증(파일 복사·사이드카 제거·pre_backup 생성 확인). 실 서버 상대로는 호출하지 않는다.
- R5 신규 4테이블은 doc_seq 미사용(자체 AUTOINCREMENT) → payroll/attendance/board/todo CRUD는 사본에서 자유롭게.

### 5.2 수기 대조 필수 항목

1. **급여 공제 합계 = 수기 계산**: 기본급 2,500,000·과세수당 200,000(과세보수 2,700,000)에서 기본요율 적용 시 국민연금 `round(2,700,000×4.5%)=121,500`, 건강보험 `round(2,700,000×3.545%)=95,715`, 장기요양 `round(95,715×12.95%)=12,395`, 고용보험 `round(2,700,000×0.9%)=24,300`, 소득세 `round(2,700,000×3.0%)=81,000`, 지방소득세 `round(81,000×0.1)=8,100`. 공제총액 `343,010`(기타 0), 식대 100,000 포함 지급총액 `2,800,000`, 실지급 `2,456,990`. → `POST /api/payroll(auto:true)` 응답의 각 공제·gross/deduction_total/net과 **정확히 일치** 확인(불일치 시 계산식 버그).
2. **수기 조정 유지**: `auto:false`로 소득세를 0으로 저장 → GET에서 income_tax=0, deduction_total·net이 그만큼 재계산됐는지 확인(서버가 gross/net 캐시 재계산).
3. **ToDo → MyPage 위젯 반영**: 사본에서 todo 3건(1건 done) 삽입 → `GET /api/mypage`의 `todos`가 **미완료 2건**만, 기한 임박 우선 정렬로 오는지 확인 → 클라 Dashboard To Do 위젯에 2건 렌더 확인(§4.8).
4. **엑셀 왕복(다운로드→업로드 dry-run 일치)**: `GET /api/io/export?type=partners`로 받은 XLSX를 `POST /api/io/import/preview(type:partners)`에 그대로 올리면 `stats.new=0`·`stats.update=거래처수`(전부 기존 코드 → 수정 판정)로 나와야 함(왕복 무손실).
5. **이관 dry-run = 스크립트 출력 일치**: `POST /api/migrate/sales/preview`의 `partner_map`·`stats`(sheet_docs/planned/skipped/item_ok/item_fail)·`period`·`total_supply`가 `node scripts/import-sales-excel.mjs --dry-run` 콘솔과 **동일 숫자**인지 대조(같은 로직 복제이므로 반드시 일치).
6. **백업 파일 생성 확인**: 사본 상대 `doBackup()` 호출(또는 실 서버 `POST /api/backup/now`) → `data/backup/erp-<stamp>.sqlite` 생성·크기>0·`GET /api/backup/list` 목록 반영 확인. WAL 체크포인트 후 복사이므로 최신 데이터 포함(빈 백업 아님).
7. **근태 월집계**: 사본에 한 사원 출근 20·휴가 2·결근 1 삽입 → `summary`의 work_days=20·leave_days=2·absent_days=1 확인(UNIQUE(사원,일)로 하루 1행).
